## 一句话

长程任务和长输入任务，都不需要长上下文也能做完。上下文短一点，准确率损失很小，成本掉一个数量级。

这篇跟老大的记忆工程是同一个命题的两面：他那一整套（prompt-inject / fact-wiki / digest / 活跃偏好）就是在做「短上下文 + 选择性读取」。这篇给了它一个理论依据和一条更硬的压缩写法。

## 一、先算清长上下文到底贵在哪

**核心事实**：生成一个 token 的计算量，随它在上下文里的位置增长。**位置越靠后的 token，生成越贵。**

这句话的分量在全篇第一段。它推翻了很多人心里的一个假设：上下文窗口是一块容量，装多装少单价一样。

云端实测（图 1，按 H100 按需价 3.85 美元每小时折算，2026 年 9 月）：

| 模型 | 256K 窗口相比 16K，每生成一个 token 贵多少 |
|---|---|
| GLM 5.2（INT4 权重） | **3.6 倍** |
| Kimi K2.6（INT4 权重） | **5.6 倍** |
| Qwen 3 Coder Next（BF16） | **7 倍** |

文章加了一句很关键的话：**零售 token 价格是按每百万 token 固定单价报的，所以终端用户根本感觉不到这个差异。** 你付的是平均价，实际算力开销被服务商摊平了。

本地实测（图 2，在 DGX Spark 上跑几个本地编码模型）：上下文拉长，**生成延迟大约翻倍**，内存占用也更大。

**还有一张对照表值得记住**（表 1）。他们把名著字数和模型窗口摆在一起：

| 作品 | 词数 | 大致 token |
|---|---|---|
| 《老人与海》 | 约 27K | 约 37K |
| 《了不起的盖茨比》 | 约 48K | 约 64K |
| 《远大前程》 | 约 184K | 约 245K |
| 《战争与和平》 | 约 566K | 约 753K |
| 圣经旧约（钦定版） | 约 603K | 约 802K |

对照的模型窗口：Claude Opus 4.5 是 200K，Kimi K2.6 是 256K，GLM 5.2 和 Gemini 3.8 Flash 是 1M，GPT 5.6 Sol 是 1.05M。

**结论**：今天的模型窗口已经装得下《战争与和平》加圣经旧约。窗口在涨，效率没涨，这两件事互相打架。

## 二、把「长上下文」拆成两类任务

他们先给了一组定义。这些定义比结论更有用，因为大部分人讨论长上下文时说的根本不是同一个东西：

| 术语 | 定义 |
|---|---|
| **推理步（inference step）** | 调一次模型产生输出。agent 工作流里通常等于一个 agent turn |
| **输入上下文** | 这一步喂给模型的全部 token：系统指令、任务输入、之前的输出、工具结果、对话历史 |
| **上下文窗口大小** | 一次调用最多能处理多少 token（架构限制或服务配置收窄后的值） |
| **长上下文** | 长度接近主流前沿模型窗口的显著比例，本文按约 **256K 以上**算 |
| **短上下文** | 长度远小于主流窗口，本文实测区间的上限约 **16K 到 50K** |
| **长输入任务** | 任务自带大量信息，直接喂进去就会形成长上下文 |
| **长程任务（long-horizon）** | 要很多步动作才能完成，后面的动作依赖前面产生的观察、产物、决定 |

**短 ≠ 小。** 作者特意补了一句：16K 到 50K 的窗口已经装得下复杂的长篇作品。说「短」是相对今天的模型窗口说的。

**两类任务的关系，是全篇最关键的一个转换**：

> 长输入任务，总能变成长程任务。做法是把长输入存成资源，再给模型一个选择性读取的工具。

一旦这么转换，「要不要一次性吞下全部材料」这个问题就消失了。材料留在文件系统里，模型按需去读。

## 三、三种上下文管理策略（下面结果里一直用这三个词）

| 缩写 | 全称（中文） | 做法 |
|---|---|---|
| **FHA** | 全历史累积 | 什么都不压，每步把全部历史塞进上下文。**这是基线** |
| **EoCC** | 对话末尾压缩 | 历史超过阈值时，压一次，保留压缩结果继续跑 |
| **SAC** | 单动作压缩 | 每执行一个动作就压一次，动作之间只传一份紧凑的语义状态 |

长输入那边还多一个手段：**选择性读取**。模型用 Bash 之类的工具去文件系统里按需翻材料，压缩只作为兜底。

## 四、三个问题，三个「是」

### RQ1 长程任务能不用长上下文吗？能

在 6 个长程基准上跑 EoCC（SWE-bench Verified 500 题、SWE-bench Multilingual 300 题、Terminal-Bench 2.1 的 89 题、FRAMES 824 题、τ²-bench 184 题、BFCLv3 200 条长上下文对话），逐步把总上下文上限和压缩阈值一起压低：

| 基准组 | 试过的「总上限 / 压缩阈值」 |
|---|---|
| SWE-bench Verified / Multilingual / Terminal-Bench / FRAMES | 48K/36K、32K/24K、24K/18K、16K/12K |
| BFCLv3 | 24K/18K、16K/12K、12K/8K |
| τ²-bench | 16K/12K、12K/8K、8K/6K |

结果（相对各自的全历史基线）：

| 模型 | 准确率变化范围 | 成本节省 | 掉超过 2 个百分点的配置数 |
|---|---|---|---|
| Claude Opus 4.5 | **-3.7 到 +5.6 个百分点** | **2.2 到 8.8 倍** | 22 个配置里最多 5 个 |
| GPT 5.6 Sol | **-3.3 到 +4.4 个百分点** | **2.4 到 5.0 倍** | 同上 |

**数字怎么读**：准确率基本是平的，有升有降，多数偏差在两个百分点以内。成本省 2 到 9 倍。这个量级的省钱幅度，作者说「跟激进的量化或结构化稀疏相当，甚至更大」。

他们还预防了一种病理：压缩导致模型重做任务、重读信息，token 总花费更多，把省下的钱吃回去。**实测一般没发生**（逐基准的 token 花费在附录 C）。

### 一个他们自己给出的反例（3.1 节，这段最诚实）

压缩是有损的。他们自己构造了一个一定失败的任务：给 agent 一个掷硬币工具，每次报告结果。压缩预算固定，迟早会丢掉某些掷硬币记录。如果某个时刻需要查第 i 次的结果，必然失败。

**但他们的解法是把修复放在 harness 层**：保留每条消息的完整记录，给 agent 一个选择性读取工具去查。查询自己的历史，就变成了长输入任务，而长输入任务上一节已经解决了。

然后他们说了一句我认为全篇最该抄下来的话：

> 我们的发现不是「你永远不需要访问对话历史」，而是「你不需要把全部对话历史放在上下文里去完成长程任务」。

**信息和上下文是两件事。** 信息要存得住，未必每次都要在场。

### RQ2 长输入任务能不用长上下文吗？能

7 个长输入基准（LongBench v2 的 503 题、LOONG 的 1600 题、AA-LCR 的 100 题，加 NIAH、RULER、Counting-Stars、BABILong 四个 needle 类）。做法：材料留在文件系统，模型用 Bash 选择性读取，压缩兜底。

| 模型 | 准确率变化 | 成本节省 |
|---|---|---|
| Claude Opus 4.5 | **-0.4 到 +40.0 个百分点** | **6.5 到 54.6 倍** |
| GPT 5.6 Sol | **+1.0 到 +30.9 个百分点** | **4.4 到 233.3 倍** |

**这里有个反直觉的地方值得停一下**：长输入任务上，压缩版的准确率经常**明显高于**一次性喂全文的基线，最高 +40 个百分点。

我对这个结果的解读是：材料全塞进去会稀释注意力，选择性读取反而让模型只看该看的那几页。**多是噪声，不是资料。**

另一个观察：对话总长度不随文档长度增长（图 7 的 LongBench v2、图 8 的 LOONG，文档长度轴取对数、对话长度轴取线性，大多数对话都压在差不多宽的带里）。**文档翻几倍，对话长度基本不动。**

配上一句支撑直觉的统计：大多数任务的**压缩次数中位数接近零**。也就是说，多数长输入任务实际需要的信息量很小，读几处就够了。

### RQ3 每个上下文只做一个动作，还行吗？行

最极端的一档：SAC，每执行一个动作就压一次，动作之间只传一份紧凑的语义状态。

| 基准 | 模型 | 全历史基线 | 最好的 EoCC | SAC | 峰值上下文 全历史 / SAC（中位 / 最大） |
|---|---|---|---|---|---|
| SWE-bench Verified | Opus 4.5 | 70.0 | 74.8 | **70.2** | 32/200K → 8/16K |
| Terminal-Bench 2.1 | Opus 4.5 | 47.2 | 52.8 | **51.8** | 27/130K → 9/19K |
| SWE-bench Verified | GPT 5.6 Sol | 84.4 | 88.8 | **82.4** | 18/173K → 7/15K |
| Terminal-Bench 2.1 | GPT 5.6 Sol | 87.6 | 88.8 | **84.3** | 17/133K → 8/37K |

**读法**：Opus 的 SAC 跟基线打平甚至更高（Terminal-Bench 高 4.6 个百分点）；GPT 5.6 Sol 掉了 2 到 3.3 个百分点。

**最扎眼的数字是峰值上下文**：中位数只有 **7 到 9K**，最大值从 13 万到 20 万 K 掉到 1.5 万到 3.7 万 K。**一个能解 SWE-bench 的 agent，每一步实际只需要七千到九千 token 的上下文。**

## 五、SSSM：把「单动作压缩」做成模型的本能

从一个观察推出来的概念：如果每步只带紧凑状态就能维持性能，那所有长上下文工作流不都能被改造成单动作工作流？

**语义状态空间模型（Semantic State Space Model, SSSM）** 是一个**后训练**出来的模型，会做五件事：

1. 读懂一段用自然语言写的对话状态
2. 对当前任务或下一步该做什么做推理
3. 执行一个动作
4. 登记动作结果
5. 把推理结论、动作决定、动作结果更新进那段状态描述里，**使得另一个推理实例能接着把对话做下去**

**跟状态空间模型（SSM）的区别**：SSM 在 token 生成之间维护一个黑箱神经状态；SSSM 维护的是**用自然语言写的、可解释的状态**。所以「semantic」。

他们给的好处是两条：token 效率高（图 1 的成本曲线），以及训练数据更省（不用教模型去注意合适的片段）。

## 六、好压缩长什么样（附录 A，全篇最可抄的一段）

结论很硬：

> 最好的压缩，**不是**忠实还原 agent 轨迹要点的那些，而是**为还没做的工作挑出相关事实**的那些。它们不是执行历史的叙事，而是为后续执行精心挑选的简报。

他们先说错在哪：把压缩当成摘要的一种特例是次优的。语言模型的摘要倾向于**给输入里所有事实同等权重**，而且容易**过度强调 agent 轨迹里重复出现的片段**，不管它跟后面要做的事有没有关系。

**能保住准确率的压缩，无论压缩频率多高，都包含这三样：**

1. **输入任务的逐字或近逐字副本**
2. **agent 当前在做什么、意图是什么、下一步计划是什么的记录**
3. **与未来执行直接相关的全部产物**，细分成：
   - 从输入任务拆出来的计划
   - 一份「什么时候算完成」的**判据清单**
   - 与上述两项相关的信息，或者指向那些产物的指针

他们还补了一句适用范围：这个结构能推广到非软件工程的工作流。**全文所有实验用的都是同一套压缩结构。**

## 七、对老大的意义

**1. 他那套系统，就是这篇论文的软实现。**
`prompt-inject.md`（每轮注入的常驻部分）= 短上下文；`fact-wiki` 四页 + obelisk 会话库 = 选择性读取的资源；`digests` 逐日摘要 = EoCC；`active-prefs` 每轮只挑几条 = SAC 的雏形（只带紧凑状态进下一轮）。

这篇的价值是：**他做对的方向有论文背书，而且论文指出了他压缩写得不够好的地方。**

**2. 附录 A 那三条，可以直接改写他的 digest 和摘要规则。**
对照一下他现在的 `86-Dreaming记忆维护\digests\`：
- 有没有**逐字保留当天任务原文**？如果他只保留自己的转述，就犯了「压缩成叙事」的错
- 有没有**「什么时候算完成」的判据清单**？他的 `PROGRESS.md` 里有目标行，digest 里大概没有
- 有没有**指向产物的指针**（文件路径）？这条他的 digest 做得不错

**我认为最该补的是第 2 条和第 3 条的「判据清单」。** 他最容易丢的不是事实，是「这件事算做完的标准」。

**3. 有一个数字可以直接用：每步 7 到 9K token。**
一个能修真实 GitHub issue 的 agent，峰值上下文中位数就这么点。他现在的常驻注入（prompt-inject + AGENTS.md + skills 描述）已经逼近甚至超过这个量级。**这篇说明「压缩到 10K 以内」不是苛刻要求，是被实测过的可行区间。**

**4. 长输入那条「+40 个百分点」提醒一件事。**
材料全塞进去会稀释注意力。**他问问题时贴一大堆背景，可能比只贴关键三段效果差。** 这条对他自己的用法也成立。

**5. 最可能翻车的地方，我列三条：**
- **模型限定。** 主实验用的是 Claude Opus 4.5 和 GPT 5.6 Sol 这种前沿闭源模型。**换成本机能跑的免费模型，压缩后掉多少完全未知**，论文没有这一档数据（开放权重只做了吞吐和附录 D 的补充实验）。
- **准确率是范围值。** 「-3.7 到 +5.6 个百分点」在 500 题的 SWE-bench 上是十几道题的差别。**「平」的意思是没崩，不是没变化。**
- **benchmark 的分布。** 这些任务都有一个共同点：答案依赖的信息量小（压缩次数中位数接近零）。**如果任务真的需要综合一百份文档，结论未必成立。** 作者自己也没否认这一点，他们说的是「在所测设置中」。

## 一句最值得记的

> 上下文短，不是省钱的技巧，是**「需要什么才拿什么」**这个原则的工程形状。

他已经在做这件事了。这篇论文告诉他两件事：方向对；压缩的写法还能再对一点。
