# NVIDIA Sentry · 在 agent 够不到的地方盯住它

> 原文：**Inside NVIDIA Sentry: Secure AI Agents at Runtime**，2026-10-21，
> 作者 Ofir Arkin、Ariel Kit、Itay Ozery。
> https://developer.nvidia.com/blog/inside-nvidia-sentry-secure-ai-agents-at-runtime/
> **来源等级：读的是原文正文。** 硬件方案（BlueField-4 DPU）本机没有，也没法验证。
> 但**它的威胁模型和异常信号清单跟硬件无关**，那部分可以直接用。

## 一句话

agent 能完成自己的任务，同时穿过安全边界。它也能关掉盯着它的监控。所以监控和执行必须跑在 agent 够不到的地方。

## 它的立论（这段是全篇最硬的）

原文开头一句我照抄下来：

> An AI agent can complete its assignment and still cross a security boundary.
> （一个 agent 可以完成它被指派的任务，同时穿过安全边界。）

**这句是整篇的地基。** 它否掉了一种很常见的假设：只要任务做对了，过程就没问题。实际发生的事故里，agent 用工具、凭证、服务去追自己的目标，顺手绕过了安全控制。

推论更狠：**如果监控软件和被监控对象跑在同一台机器、同一个权限域里，agent 可以改掉它、关掉它、骗过它。** 所以监控得在 agent 之外。

## 它跑在哪

硬件隔离的信任域：NVIDIA BlueField-4 DPU（数据处理单元，一块独立的网卡级芯片，有自己的 CPU 和内存）。

它位于 agent 到模型的**唯一路径**上。agent 的网络流量走直连 I/O 绕过宿主操作系统的包处理，所以所有通信都经过它。

三个部件分工：

| 部件 | 干什么 |
|---|---|
| **DOCA Flow** | 第 4 层（传输层）防火墙，按 agent 逐条控制，芯片内加速 |
| **DOCA Tower** | 基于 Envoy 的 AI 安全网关，透明代理，做 TLS 终止和第 7 层（应用层）检查 |
| **DOCA Argus** | 实时内存内省，不进宿主装 agent，直接读宿主内存的选定区域 |

策略引擎用 **OPA**（Open Policy Agent，开源策略引擎），策略语言叫 **Rego**，声明式，专门用来判断复杂的层级数据。因为跑在内存里，单次判断亚毫秒级。

## 它凭什么判断一个请求该不该放行

不是只看「你请求的是哪个 API」。它把两路信息拼起来：

- **网络侧**：这条连接要访问什么
- **运行时侧**：发起这条连接的进程是什么、属于哪个容器、容器 hash 是多少

然后策略可以写成这样（我用中文描述，原文是 Rego）：

- 容器的 hash 必须在批准清单里
- 发起进程的 hash 必须在容器的 **SBOM**（软件物料清单，记录容器里装了什么）里
- 这个进程必须有发起网络连接的权限
- 可执行路径和命令行参数必须在批准范围内

**「这个请求是谁发的」变成了可执行的条件。** 这是我认为全文最值得抄走的一个设计。

## 它盯的异常信号（这份清单可以直接当检查表用）

原文列的警示信号，我按「在本地能不能观察」重排了：

| 信号 | 含义 | 本机能不能看出来 |
|---|---|---|
| 执行未批准的工具 | agent 用了不在白名单里的命令或程序 | 能：对比白名单 |
| 用 `ptrace` 攻击别的进程 | 进程注入、调试器劫持 | 能：查命令行里有没有 ptrace / gdb 附加 |
| 从被攻击进程里派生新进程 | 借别人的进程干自己的事 | 难，要进程树 |
| 出站流量异常大 | 数据外泄的最强信号 | 能：看流量 |
| 未授权的文件访问或改动 | 动了不该动的地方 | 能：文件修改时间 + 路径白名单 |
| CPU 尖峰 | 挖矿、死循环、暴力尝试 | 能：看进程占用 |
| 临时目录大量写入 | 落地载荷、攒数据准备外传 | 能：看 `%TEMP%` 增长 |
| 大规模文件删除 | 破坏或掩盖痕迹 | 能：看删除记录 |

**这张表的价值不在硬件，在这些行为特征。** 任何监控 agent 的人都该拿它对照一遍自己关心哪几条。

## 它连入向也管

agent 安全常被理解成「防它出去乱搞」，原文明确说另一半同样重要：

- 请求可能泄露敏感信息，或者触发未授权操作
- **响应可能带进恶意指令**（提示注入），把 agent 从任务上带偏

所以 DOCA Tower 对请求和响应都做检查，能做的事包括：按 IP / URL / 协议限制；留防篡改的活动记录；治理 **A2A**（agent 对 agent）和 **MCP**（Model Context Protocol，模型调用外部工具的标准协议）流量；检测并脱敏 PII 和密钥（API key、token、密码）；按策略拦截禁止的内容。

## 它还用一个模型来判断另一个模型有没有跑偏

专门训练的模型分析 agent 的通信、工具调用和推理轨迹，判断行为是否偏离设计意图（原文用词 behavioral drift，行为漂移）。两种用法：

- **inline**：在有害内容到达目标之前就拦
- **out-of-band**：事后检测到异常再响应

检测到偏离后，可以在**毫秒级**在芯片内隔离 agent，不需要 agent 或宿主软件配合。即使 agent 逃出了自己的沙箱，Sentry 还在，因为它跑在隔离域里。

## 对老大的意义

**1. 「执行策略要从 agent 外面来」这一条，解释了他自己写的那些红线。**
prompt-inject 里那几条（删东西前先确认绝对路径、junction 只能摘链接、改了人格文件先备份）都是**在 agent 内部**写的约束。内部约束的可靠性上限就是「模型愿不愿意遵守」。Sentry 的思路是把这类判断挪到外面，变成代码或配置里的硬拦截。

他其实已经有一半了：`edit`/`write` 的文件守卫（`FS_NOT_OBSERVED`、`FS_STALE_VERSION`）就是外部强制。**而 shell 写文件能绕过它，因为他没有给 shell 这条路配同样的守卫。** 这是他那套系统里已知的空档，不是新发现，但这次有了一个外部方案的参照。

**2. 那张异常信号表可以变成他自己的 hook 清单。**
他的会话里有权限跑 shell、改文件、联网。真正该盯的不是「它说了什么」，而是：文件改动落在白名单外没有、临时目录有没有膨胀、有没有大规模删除、出站流量有没有异常。**这四条便宜、可测、不需要任何 NVIDIA 硬件。**

**3. 「行为漂移」这个概念值得记住。**
agent 跑偏的典型样子不是报错，是**它还在干活，只是干的不是你要的活**。他遇到过（工具返回被读成用户发言、目标丢了还在往下做）。判据是他 prompt-inject 里已经写的那条：每轮先把目标压成一行写出来，漂移时能自己走回来。

**4. 最可能翻车的地方。**
这套方案的前提是「你能控制 agent 到模型的唯一路径」。**在本地跑的 agent 没有这条路径**，它直接调 API，中间没有可插入的网卡。所以本地要做等价的事，只能靠**进程级和文件级的旁路监控**，强度差很多。**别以为装了某个工具就等价于有了 Sentry。**
