# GLM-5.3 双机 vLLM · 一个模型为什么装不下一张卡

> 原文：**When One GPU Isn't Enough: Serving GLM-5.3 Across Two NVIDIA DGX Stations with vLLM**，
> 2026-11-13，作者 Fatima Fall。
> https://developer.nvidia.com/blog/when-one-gpu-isnt-enough-serving-glm-5-3-across-two-nvidia-dgx-stations-with-vllm/
> **来源等级：读的是原文正文，但只到第 5 步 AIPerf 压测的开头。** 吞吐数字来自原文的 AI 生成摘要和正文表，没看到完整压测表。
> **本文描述的操作本机无法复现**（没有 GB300，没有 RDMA 双机）。读它是为了搞懂概念，不是照着做。

## 一句话

753B 的模型量化后仍要 464 GB 显存，单卡 252 GB 装不下，于是拆成两半放在两台机器的两张卡上，对外还是一个 OpenAI 兼容端点。

## 数字先摆清

| 项 | 值 | 这数字意味着什么 |
|---|---|---|
| GLM-5.3 NVFP4 总参数 | 753B | MoE（混合专家）架构 |
| 每 token 激活参数 | 40B | 稀疏激活，算得少 |
| 权重大小 | 约 464 GB | 全都要在显存里 |
| 单张 GB300 HBM3e | 252 GB | 装不下，差一半 |
| 张量并行度 | TP = 2 | 每卡约 218 GiB 权重 |

**这里有个容易搞错的点**：MoE 稀疏激活只减少**计算**，不减少**显存**。因为每个 token 可能被路由到不同的专家，所以全部权重都得随时待命。文章原话就是这个意思。**「激活 40B」不等于「只需要 40B 的空间」。**

## 为什么要两台机器而不是一块大卡

因为单卡上限就到了。装不下的时候有三条路，文章选了第二条：

1. **量化到能塞进一张卡。** NVFP4 已经用上了，还不够。
2. **张量并行（TP，tensor parallelism）：把权重和计算切到多张卡。** 选了这条，TP=2。
3. **CPU offload：把部分权重放内存。** 明确关掉了。说明他们的判据是「宁可上第二台机器，也不让权重走 PCIe 和内存」。

这个取舍对没有硬件的人是纯概念，但它说明了一件事：**推理的第一瓶颈是显存容量，不是算力。** 装不下就没得谈。

## 关键参数，一个都不能瞎改

```
--max-model-len 98304          # 上下文上限 96K token，输入加输出一起算
--gpu-memory-utilization 0.93  # 给 vLLM 93% 显存
--kv-cache-dtype fp8           # KV cache 用 fp8 存，内存减半
--enable-prefix-caching        # 见过的提示前缀不重算
--max-num-seqs 16              # 同时在跑的请求数上限
--block-size 128
--speculative-config '{"method":"mtp","num_speculative_tokens":4}'
```

逐个解释，这些词以后还会遇到：

- **KV cache**：模型生成时缓存每个 token 的 Key/Value 向量，避免重复计算。它随上下文长度和并发数线性涨，是显存第二大占用。
- **prefix caching**：多个请求共享同一段开头（系统提示、工具定义）时，只算一次。
- **投机解码（speculative decoding）**：小模型或模型自带的草稿层先猜几个 token，再用完整模型验证。猜对了就一次出好几个 token。这里的 `mtp`（multi-token prediction，多 token 预测）就是模型的草稿层一次草 4 个。**收益完全取决于猜中率，而猜中率随提示内容变**，所以同一个配置换一种任务，加速比会差很多。
- **max-num-seqs**：并发上限。设得太高会抢 KV cache，设得太低会排队。

文章给了一条很实用的纪律：**改其他参数一次只改一个，改完重新测。**

## 两个必须验的东西（这段是全文最值钱的部分）

**1. 走的是 GPU Direct RDMA，不是 TCP 回退。**
两台机器互通，如果网卡没配对，NCCL（NVIDIA 的集合通信库）会**静默降级**到普通 socket，性能掉一个数量级但不报错。验证要靠读 NCCL 日志：

```bash
grep -hE "NET/IB.*GDRDMA|GPU Direct RDMA Enabled" /tmp/nccl_*.log
# 没有这一行就是降级了
```

**2. 权重真的被劈成两半了。** `nvidia-smi` 里每张卡约 218 GiB，等于 464 的一半。看到一张卡满载、另一张闲着，说明并行没生效。

还有一条坑写在启动脚本注释里：**NCCL 用镜像自带的 2.30.7**，更老的版本在跨节点 RoCE 上重放 CUDA graph 会死锁（vLLM issue #52504）。这类「版本对了才不卡死」的问题，报错信息通常看不出来。

## 性能曲线的形状

用 AIPerf 压测，数据集是 SPEED-Bench 的 80 条真实编码对话：

| 并发 | 输出吞吐 | 备注 |
|---|---|---|
| 16 | **607.8 tok/s** | 峰值 |
| 32 | 385.0 tok/s | 平均请求延迟 453.5 秒 |

**并发翻倍，吞吐反而掉了。** 原因不难猜：KV cache 不够分，请求互相挤，排队时间吃掉了吞吐。这个形状值得记住：**并发不是越大越好，有一条拐点，拐点前面加并发提吞吐，拐点后面加并发只加延迟。**

文章自己的建议是：拿自己的真实提示重跑一遍 AIPerf，找这个工作负载的最优并发。**别人的拐点不是你的拐点。**

## 对老大的意义

**1. 三个词的关系搞清了，「量化 / 分片 / offload」是三档不同的手段。**
量化是少存一位，分片是把活分给多个人，offload 是把东西搬出显存。装不下时的尝试顺序是：先量化，再分片，最后才 offload（因为 offload 每次都要走总线）。

**2. 为什么 API 的延迟不能按「单机算力」估。**
一个端点背后可能是两台机器，谁也单独答不了一句，每个 token 都要在网线上换一次中间结果。他的免费额度接的那批模型，标的延迟通常是别人的最优值，**自己压一遍才是真的**。

**3. KV cache 是「并发 × 上下文长度」的乘积。**
他每天在调上下文长度（prompt-inject 有几 KB、digest 有多少条），这条公式在云上和在本地是同一条：**上下文越长、同时开的会话越多，能跑的量越少。** 这也解释了为什么长上下文模型贵得不线性。

**4. 最可能翻车的地方。**
这套配置里任何一个环境变量写错，表现都是「慢」或者「卡住」，不是「报错」。**没有那两步验证，你会以为自己部署成功了。**
