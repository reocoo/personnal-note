# Agent Substrate · 把闲置的 agent 快照出去

> 原文：**Agent Substrate: Advancing Kubernetes for Agents at Scale**，2026-11-10，
> 作者 Ekin Karabulut、Omer Yahud。
> https://developer.nvidia.com/blog/agent-substrate-advancing-kubernetes-for-agents-at-scale/
> **来源等级：读的是原文正文。** 文中没有公开的独立第三方复现，性能数字（10 倍密度）是项目方自述。
> 代码在 github.com/agent-substrate/substrate，已捐给 CNCF Sandbox（云原生基金会的沙箱项目档位，意味着还不是稳定生产项目）。

## 一句话

agent 大部分时间在等，Kubernetes 不知道自己在等什么，于是要么白烧算力，要么每轮冷启动几秒。
Agent Substrate 的做法是把「状态」快照出去，「执行」放进共享池。

## 它要解决的问题

传统 Web 服务是少数几个长命实例。agent 不是这个形状：

1. 醒来，做一步（跑一条 shell、改一个文件、调一次测试、调一次模型）
2. 等，可能几毫秒，可能几分钟
3. 再醒来，状态（文件系统、进程、工作目录）必须还在

Kubernetes 起一个 Pod 要走 API server、admission、etcd、调度器、kubelet、拉镜像、配网络，**这几秒对一个要跑 10 毫秒 bash 命令就退出的沙箱来说太慢**，而这类沙箱每秒要出现几百次。

平台团队于是只剩两条烂路：

| 烂路 | 代价 |
|---|---|
| 每个 agent 一个常驻 Pod | agent 几乎总是闲着，算力白烧 |
| 每轮现建 Pod | 每一步都付几秒冷启动，还丢状态 |

## 怎么做的

**用 K8s 管一小池预热好的 worker Pod，另起一个控制平面，把大量 actor 映射到这池 worker 上。**

- actor = 一个 agent 加上它的运行环境
- actor 空闲 → 整个沙箱（gVisor 或 microVM）被快照出去，内存和文件系统一起存，worker 释放
- actor 再次被调用 → 恢复到**任意一个**空闲 worker 上，状态完整

关键在于：唤醒不需要重新走 API server / 调度器 / kubelet。worker Pod 仍然是普通 K8s Pod，所以集群调度、配额、放置策略照旧生效。

**密度**：自称比标准容器高 10 倍，目标是安全跑几百万个 agent 和工具。安全模型是零信任（默认不相信沙箱里的任何东西）。

## 三类负载（判断你的场景是不是这一类）

**1. 编码助手。** LLM 调用和仓库操作交替。用户期望环境在轮次之间保持，并且立刻响应。一个平台服务几千个会话，不可能每个会话配一个常驻沙箱。

**2. RL 后训练的 CPU 环境。** 带可验证奖励的强化学习，GPU 训练器和生成服务旁边挂着大量 CPU 重的环境（代码沙箱、编译器、浏览器、模拟器），执行动作并检查结果。沙箱需求是**突发**的：rollout 批次一次派发大量动作。规模从早期几百个涨到生产的几十万个。**最慢的那个环境决定训练器什么时候拿到下一批**，所以这条路径上任何冷启动都让 GPU 干等。

**3. 研究用短命 GPU 沙箱。** 研究者的编码 agent 要一块 GPU，不是为了服务模型，而是编译 CUDA 代码、benchmark 一个 kernel、跑一次数值计算。用完就删。这要求大量短命、隔离的 GPU 沙箱，启动快，还要在有限 GPU 池里公平共享。

## 上游做了什么（都可以查 PR 号）

| 改动 | 解决什么 | 链接 |
|---|---|---|
| 路由层请求排队 | 所有 worker 都忙时，新请求**等**而不是直接报错。带等待上限和排队数量上限 | PR #221、#1229 |
| microVM 沙箱的每容器 CPU / 内存限额 | 一个跑飞的日志/代理容器不能吃掉整个沙箱的内存把 agent 带走 | PR #859 |
| 基于 K8s DRA 的 GPU 暂停/恢复 | 让 agent 在等人工审核时先放开 GPU，恢复时编译产物和数据还在 | issue #752 |

**GPU 快照有个绕不过去的硬件约束**：GPU checkpoint 通常只能恢复到**同型号** GPU，有时还要求同驱动版本。他们的设计是让设备厂商声明「怎么安全暂停自家设备」「快照依赖哪些设备属性」，快照时把属性一起记下，恢复到匹配的设备，匹配不上就退回一次干净的冷启动。设计是厂商中立的，NVIDIA GPU 第一个支持。

这条对任何做「挂起再恢复」的人都成立：**状态能存下来，不等于能在另一台机器上接着跑。**

## 和 Dynamo 的分工（这段最有迁移价值）

Agent Substrate 管 agent 在哪执行，NVIDIA Dynamo（开源分布式推理框架）管模型在哪思考。两者面对的浪费是同一个形状：让空闲沙箱热着浪费 CPU 和内存，重复调用时重建模型上下文浪费 GPU。

分工很干净：

- **Substrate**：管 agent 环境的高频生命周期（激活、挂起、恢复）
- **Dynamo**：管推理的高性能生命周期（KV cache 放哪、prefill/decode 谁忙）
- **router 在中间**：知道可复用的 KV cache 在哪个 worker、GPU 池的负载

传统推理路由把每次模型调用当成独立请求。agent 里每次调用是长循环里的一步，连续几次调用**复用同一份系统提示、工具定义、对话历史**。所以 router 需要额外信号：会话身份、请求优先级、预期输出长度、工具调用边界、生命周期事件。有了这些它才能：

- 把相关的模型调用钉在已经持有可复用 KV cache 的 worker 上，同时不制造 GPU 热点
- 推理池紧张时，交互轮优先于后台 agent 工作
- 在工具调用的间隙里保住系统提示和对话历史
- **优先丢弃已终止子代理、已关闭的推理分支、已摘要的上下文的 cache**

反向也通：Dynamo 把推理信号回传给 Substrate，包括首 token 时间（TTFT）预测、完成时间预测、请求进度、cache 就绪度、GPU 池饱和度。Substrate 拿这些决定：让 actor 常驻、在长推理等待期间挂起、还是在模型响应快回来时提前恢复。

一句话概括这个循环：**模型调用 → 工具调用 → 观察 → 再模型调用。**

## 对老大的意义

**1. 「状态」和「执行」分开，是他自己的记忆系统在做的事。**
他的 dreaming / prompt-inject 那套，本质就是把状态（偏好、事实、digest、活跃偏好）快照到文件，执行时再恢复进上下文。这篇文章是同一件事在集群规模上的版本。差别在于：他恢复一次要花 token，人家恢复一次是拷贝内存。**所以「上下文短一点」不是洁癖，是同一个效率问题的小号版本。**

**2. 「KV cache 感知路由」解释了一个日常现象。**
同一会话连续调用同一家模型会变快，换一家就慢，因为缓存没了。文章里那条「优先丢弃已关闭分支的 cache」可以直接借来管上下文：**摘要过的旧对话该主动扔掉，别留着占位置。**

**3. 判断真假的标准。**
10 倍密度、几百万 agent 都是作者自述，没有第三方复现。这个项目还是 CNCF Sandbox，API 自己在文章里承认「还在变」。当概念学可以，当稳定方案用不行。

**4. 最可能翻车的地方。**
这套东西的收益全来自「多数时间在等」。如果一个 agent 是连续重活、几乎不等，常驻沙箱反而更省。**先测自己的等待占比，再谈要不要换架构。**
