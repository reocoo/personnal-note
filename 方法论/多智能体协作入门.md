# 多智能体协作：初学者能用的判断

> 这篇回答五个问题：多智能体有没有必要、和上下文工程与意图工程什么关系、记忆在里面干什么、
> 主流项目怎么拆任务和协调、人类注意力能不能解放。
>
> **材料**：两篇立场相反的原文我亲自读了，六个主流项目的实现细节来自一次专项调研（全部读到官方原文）。
> 具体出处每条都标了，读不到原文的地方明确标「未读」。
> 采集时间 2026-11-14。**多智能体这个领域的结论半年就会过期**，用时先看日期。

## 一句话

多智能体不是「更强的团队」，是**用并行换上下文容量**的一种手段。它的代价在协调，不在模型。

## 一、先把两篇立场相反的原文摆出来

### 反方：Cognition（Devin 的团队）2025-06，《Don't Build Multi-Agents》

https://cognition.com/blog/dont-build-multi-agents

他们给了两条原则，然后说「值得违背这两条的时候很少，应该默认排除不遵守它们的架构」：

1. **共享上下文，要共享完整的执行轨迹，不是单条消息**
2. **每一个动作都携带隐含决定，冲突的决定导致坏结果**

那个例子我照抄下来，因为它比任何定义都好懂：

> 任务是「做一个 Flappy Bird 克隆」。拆成两个子任务：A 做带绿管的移动背景和碰撞箱，B 做可上下移动的鸟。
> 结果 A 误解了，做成了超级马里奥风格的背景；B 做的鸟不像游戏素材，移动方式也不对。
> 最后主 agent 剩下的活，是收拾两个误解拼在一起。

他们还堵了「那我把原任务也传给子代理」这个补丁：真实系统里对话是多轮的，主 agent 为了拆任务已经调过工具，任何细节都可能影响对任务的解释。

**他们的结论**：2025 年跑多个 agent 协作只能得到脆弱的系统，决策太分散，上下文传不透。
**他们的做法**：单线程线性 agent，加一个专门做压缩的模型（他们为此微调过小模型）。

### 正方：Anthropic《How we built our multi-agent research system》

https://www.anthropic.com/research/multi-agent-research-system

**数字先摆**：

| 指标 | 数值 |
|---|---|
| 多智能体研究系统 vs 单 agent（内部评测） | **高 90.2%** |
| BrowseComp 上 95% 的性能方差，token 用量单独解释 | **80%** |
| agent 相比聊天用多少 token | **4 倍** |
| 多智能体相比聊天用多少 token | **15 倍** |
| 并行化后复杂查询耗时 | **降 90%** |

**他们也写明了什么时候不行**，原文意思：需要所有 agent 共享同一上下文的领域、agent 之间依赖多的领域，目前不适合。多数编码任务真正可并行的部分比研究少，而且现在的模型还不擅长实时把活派给别的 agent。

### 我的判断：两边不矛盾

它们在说两种任务形状。

| 任务形状 | 谁说得对 |
|---|---|
| 可并行、信息量超单窗口、工具多（调研、审计、批处理） | Anthropic |
| 强共享上下文、强依赖、同一份文件反复改（多数编码） | Cognition |

Cognition 那句话值得单独记：他们说「当单线程 agent 更善于跟人沟通时，跨 agent 的上下文传递会免费到来」。这句话把问题定性了：**多智能体的瓶颈一直是「传递」，不是「智能」。**

## 二、有必要吗：按形状判，别按大小判

| 判据 | 值得用多智能体 | 不值得 |
|---|---|---|
| 子任务之间要不要看对方的过程 | 不需要，只要能拿到结果 | 需要，边做边看 |
| 子任务能不能切出互不相交的写边界 | 能（各写各的文件） | 不能（改同一份） |
| 信息量是否超过单窗口 | 超过，必须分段处理 | 装得下 |
| 依赖关系 | 少，可以同时开始 | 多，B 必须等 A 的真实输出 |
| 返工代价 | 高（一步错要重做几十步） | 低（改两行） |

五条里四条偏「不值得」，就别上。**多数编码任务落在右边。**

## 三、跟上下文工程、意图工程是什么关系

多智能体是**上下文工程里「隔离」那一招的延伸**。前面笔记里那三个动作（选、压、界），它解决的是「界」。

两种理解都对，取决于你从哪边看：

- **Cognition 的角度**：多智能体是上下文工程的一种失败模式。因为上下文共享不了，所以才出问题。
- **Anthropic 的角度**：它在 token 维度上做扩展。每个子代理有独立窗口，等于凭空加了几份容量。

**意图工程在这里变得更贵，不是更便宜。**

Anthropic 的第 2 条工程原则原文是「教编排者怎么委派」。他们早期的失败很典型：主 agent 只给一句「研究半导体短缺」，结果一个子代理去查 2021 年汽车芯片危机，另外两个重复查 2025 年供应链，等于没有分工。

一句话：**意图含糊，在单 agent 里表现为「答偏」，在多 agent 里表现为「重复劳动」。**

## 四、记忆扮演什么角色

三处，都是硬需求，缺一个就崩。

**1. 主编排者的计划必须落盘。**
Anthropic 原文：主研究员第一件事是把计划存进 Memory，因为上下文一旦超过 20 万 token 会被截断，计划必须留下来。这条和你本机的 `PROGRESS.md` 是同一个东西。

**2. 阶段摘要 + 干净的新子代理。**
完成一个阶段就压缩一次，然后开一个上下文干净的新子代理，从记忆里把计划取回来。这是「压缩」和「隔离」两招的组合用法。

**3. 产物走文件系统，不走对话。**
他们附录里那句最值钱：让子代理把结果写成文件，回传给协调者的只是一条轻量引用。原文的说法是避免「传话游戏」造成的信息损失。

这条在本机是可验证的：DSH 的结算通道只搬子代理**最后一条**消息，前面 step 的正文全丢。所以「产物落文件 + 回传路径」不是优化，是必需品。

## 五、六个主流项目各自怎么做的

全部读到官方原文（MetaGPT、ChatDev 读论文 HTML；AutoGen、CrewAI、deepagents、A2A 读官方文档）。

| 项目 | 拆分依据 | 协调机制 | 人介入点 | 官方承认的局限 |
|---|---|---|---|---|
| **MetaGPT** | **角色 + 中间产物格式**。5 个固定角色，上一环的交付物（PRD、接口定义、文件清单）就是下一环的输入契约 | **共享消息池 + 订阅**，没有中心调度器。用文档不用对话。代码靠真跑单测兜底，最多重试 3 次 | 开头提需求、结尾看产物。**论文附录承认中途打断和设 checkpoint 是难题** | 做不了 UI/前端；撑不住真实复杂需求；幻觉沿链放大 |
| **ChatDev** | **阶段 + 子任务的硬编码链**。3 阶段 5 子任务 5 角色，每个子任务固定 2 个 agent（指导者 + 执行者） | 链式顺序推进。记忆分短期和长期两层。用「让执行者先反问」去幻觉。子任务 10 轮或代码两次没变就收 | 开头一句需求，之后全自动 | 信息密度低；需求不清就退化；**只适合原型不适合真实系统**；多 agent 更贵更慢 |
| **AutoGen / AG2** | **不预设，给你几种模式选**（轮流 / 模型选人 / 交接 / 编排器） | AG2 用 `GroupChatManager` 选人加广播，四种策略；新版用 LLM 选人；靠终止条件收场 | `UserProxyAgent` 中途插话，**会阻塞并且状态不可保存** | 官方劝先用单 agent；群聊会死循环（官方硬加 25 条消息上限）；Magentic-One 带 6 条安全警告 |
| **CrewAI** | **任务对象 + 显式 `context` 依赖**。顺序模式按数组，层级模式由 manager 按能力派活 | 两种 Process（顺序 / 层级）。同级靠两个自动工具（甩活、问同事）。Flows 提供事件驱动的确定性编排和共享 state | 任务级 `human_input=True`，交最终答案前问人 | **官方不建议直接拿 Crew 上生产，让你包一层 Flow**；层级模式缺 manager 就报错 |
| **deepagents**（LangGraph） | **以上下文窗口为单位**。`write_todos` 加 `task()` 分包 | 主 agent 调 `task()`，子 agent 独立跑完只回一份报告。isolated 和 fork 两种上下文模式。大块数据落虚拟文件系统 | **工具级 `interrupt_on`**，改文件等危险动作前暂停，可批准或改参数 | 子代理无状态只能回一次；fork 的子代理不能再派活；官方专门写一节讲三种失效 |
| **A2A**（Agent2Agent） | **协议不管内部拆解**，按对方 Agent Card 里声明的 skills 派活 | 客户端 / 服务端两角色，客户端天然是编排者。HTTP + JSON-RPC。**刻意不共享内部状态** | 只提供 `input-required` 和 `auth-required` 两个状态位，**不定义审批流程** | 制品版本追溯被排除在规范外；任务终态不可重启 |

### 同一个问题，六家六种答案

MetaGPT 按「文档交接」拆，ChatDev 按「阶段对话」拆，AutoGen 按「谁下一个说话」拆，CrewAI 按「任务依赖」拆，deepagents 按「上下文预算」拆，A2A 干脆不拆，只负责把活交给别人。

**没有一种是普遍正确的。** 选哪个取决于你的任务长什么样。

### 三个值得记住的对照

**1. 人的位置在往下降，也在往细里走。**（这条是调研方的推断，不是原文）
MetaGPT 把人放在流程两端，能看整份 PRD，但中途打断很难；AutoGen 把人做成一个 agent 塞进群里；CrewAI 挂在任务出口；deepagents 挂在**单个工具调用前**。越往后介入点越具体，但每次能看到的范围越小。

**2. 协调机制有两条路线。** 一条是「共享消息池 + 订阅过滤」（MetaGPT、AutoGen 的广播），信息在池子里；另一条是「点对点单次交接」（deepagents 的 task、A2A 的 task 对 task），信息不共享只传结果。后者省上下文，但中途没法追问。**这正好对应 Cognition 和 Anthropic 的分歧。**

**3. 失败大多不是模型答错，是协调出错。** 官方示例自己就展示了两类事故：AutoGen 的示例里数据分析角色拿到错误数字算出 21.99%；deepagents 专门写一节讲「没叫 subagent」「叫错 subagent」。这两类都不是推理问题，是调度问题。

### 一个反直觉的发现

**MetaGPT 在正文里说自己给人「最高级别控制权」：可发起、可观察、可停止。但在论文附录的局限里承认：用户难以中断某个 agent 的运行，也难以给它设 checkpoint。**

真正把「暂停等人」做成运行时原语的，是后来的工程框架：deepagents 的 `interrupt_on`（工具级审批），A2A 的 `input-required`（状态位）。

**这说明一件更大的事：早期论文里「人在回路」是叙事，不是机制。** 判一个框架支不支持人介入，别看它文档里怎么宣传，去看它的 API 里有没有一个「停下来的原语」。

## 六、人类注意力能不能被解放

**能解放执行注意力，不能解放判断注意力。而且它会改变判断的形状。**

三个证据：

**1. 自动化评测会漏掉真实的判断。**
Anthropic 原文：人工测试发现他们早期的 agent 系统性地偏好 SEO 内容农场，忽略学术 PDF 和个人博客这类更权威但排名低得多的来源。这个偏差 LLM 当裁判打不出来。

**2. 冲突最终要人来收。**
Cognition 那个 Flappy Bird 例子，最后那一步「收拾两个误解」没有任何自动机制能替代，因为两个子代理谁都认为自己是对的。

**3. 成本涨 15 倍，输出也变成 4 份。**
你要审的东西从一份变成四份，而审阅是注意力最密集的活动。

**我的判断**：注意力被**转移**，不是被解放。从「干活」转到「审阅」，而审阅更累。

真正能解放注意力的做法是另一件事：**把判断标准写成可执行的门槛**。让它自己判通过 / 不通过，人只看失败案例。这是意图工程的终点，也是为什么它比多智能体更值钱。

## 七、给老大的落地判据

**本机三条硬约束**（实测）：

| 约束         | 数值       | 含义                          |
| ---------- | -------- | --------------------------- |
| `maxDepth` | 1        | 只能一层：主会话带子代理，子代理不能再派        |
| 名册上限       | 8        | 含主会话共 8 个                   |
| 结算通道       | 只搬最后一条消息 | 子代理必须用 `send_message` 交完整报告 |

**五条自检**（照着问，任何一条答「否」就先别上）：

1. 能把任务拆成 5 个以上**互不相交的文件路径**吗？
2. 子任务之间需要看对方的过程吗？（需要就别拆）
3. 一场任务超过 20 步吗？（不到就别拆）
4. 有明确的验收命令吗？（没有就别拆，拆了也没人判对错）
5. 返工一次要重做多少步？（少于 10 步就别拆）

**最小可行组合**（不引入中间层）：

1. `BRIEF.md` 写意图，先给你确认
2. 一张任务板，状态外部化
3. 子代理输出契约：六段，每条结论带证据路径
4. 一个只读审查者
5. 主会话保留「抽查验收」这一个动手动作

## 八、术语速查

| 词 | 一句话 |
|---|---|
| 编排者（orchestrator） | 负责拆任务和派活的那个 agent，也叫 lead |
| 子代理（subagent） | 拿一个子任务、有自己上下文窗口、只回结果的 agent |
| 交接（handoff） | 把控制权连上下文一起交给另一个 agent |
| 群聊模式 | 多个 agent 在同一个消息池里，按规则轮流发言 |
| 任务板 | 外部化的状态，谁在做什么写到文件里，不靠对话记忆 |
| 制品（artifact） | 子代理产出的文件，传给别人的是路径不是内容 |
| 人在回路（HITL） | Human in the loop，人在某一步批准或修改 |
| 不透明执行 | A2A 的原则：我不共享内部状态，只给你结果 |
| 上下文预算 | 一个子代理能分到多少窗口，deepagents 的拆包依据就是它 |

**没读到原文的**：

- CrewAI 的 HITL 工作流页、Flows 人工反馈页
- MetaGPT 官方文档站（只读了论文）

**明确不能这么用的**：
- **跨论文比较 token 数没有意义**。模型、温度、数据集都不同（ChatDev 用 GPT-3.5 + temperature 0.2，MetaGPT 多组实验用不同 LLM）。只有 MetaGPT 论文自己做过同台对比。
- MetaGPT 那句「100% 任务完成率」，论文没说清是在哪个子集上算的。
- 「角色越多越好」只有 4 行消融表支持，样本 7 个任务，不能外推。

**时间边界**：这批判断的依据是 2025 年中到 2026 年中的材料。Cognition 那句「等单线程 agent 更会跟人沟通，跨 agent 上下文传递会免费到来」，到 2026-11 是否已经发生，本笔记没有核实。
