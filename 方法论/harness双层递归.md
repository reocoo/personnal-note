# Harness² 双层递归：可复用经验

> 从 Google `Harness²`（arXiv:2610.14224）提炼的方法论，**不含它的分数** —— 那部分有问题，见文末「不该抄的」。
> 该读它的时机：你要设计「能自己变好」的系统、要拆提示词结构、或要判断一篇自我改进论文能不能信。

## 一句话

**不改模型，只改模型外面那层可 diff 的文件；而且不传成品，传经验。**

---

## 一、先分清两个层级（这是全套的地基）

| 概念 | 是什么 | 好坏怎么变 |
|---|---|---|
| **执行 harness** | 围绕模型的提示词、护栏、记忆、工具说明、技能、脚本、子代理、插件 | 只对**当前任务**变好 |
| **改善 harness** | 「怎么改执行 harness」的那套方法 + 经验库 | 对**以后所有任务**变好 |

它的核心主张不是「让 AI 改自己代码」那种玄的，而是：**Agent = 模型 + harness**，权重冻结，只搜索 harness。所以每一步都是一次 diff，可审计、可回滚、可读。

**为什么这很关键**：一旦改动表现为文件 diff，你就能回答「是这处改动让它变好的吗」。这是整个方法能成立的前提。

---

## 二、内层：任务级递归（Propose → Probe → Compose）

### 三个动作

| 步 | 做什么 | 关键细节 |
|---|---|---|
| **Propose** | 起草改动候选 | **两个独立角色**：*不变式编辑器*只管跨领域通用毛病（规划、工具调用、上下文管理、委派）；*领域编辑器*只管这一行的知识与流程 |
| **Probe** | 同任务、同模型、同环境重跑候选，比对轨迹与产物 | 问的是「这处改动**动到它想动的那个行为**没有」，**不问「产物对不对」** |
| **Compose** | 读参考 + 候选 + 各自 diff + 全部执行证据，选择性合并 | 可合并、可改写冲突、可只采一个、**可原样保留**。每项决定必须绑一条具体观察，不能绑「预计涨几分」 |

### 为什么 Probe 能不要标准答案

因为它换了个问题：从「这对吗」（要标签）换成「**这改动有没有造成它想造成的变化**」（只要两次执行）。

这是因果问题，不是价值问题。所以它比「让另一个 LLM 打分」干净。

### ⚠️ 但这条必须一起记住

**行为变了 ≠ 变好了。** Probe 只能证伪，不能证真。

论文自己的失败案例就是证据：有个产物 **55 分被选中、95 分的被丢掉**；另一个因为覆盖变窄，54 分掉到 26 分。

→ **用这套方法时，一定要另配一个「不看行为、只看结果」的最终验收。** 否则你会用自己的偏好骗自己。

### 预算 k 的两种花法

| 形式 | 干什么 | 特点 |
|---|---|---|
| **并行** | 一次提 k 个不变式 + k 个领域候选，产出 k 个合成体 | 探索**更宽** |
| **顺序** | 把上一轮改好的 harness 与证据带入下一步，串 k 轮 | 探索**更深** |

实测（它的数据）：k 从 1 到 5，两种都单调涨，但**并行最后略高**。而且 k=2 就已经超过所有基线在 k=5 的水平 —— 说明**方法有效性的来源不是「多试几次」**。

## 三、外层：驾驭级递归（最值钱的一个设计）

### 做法

每个任务做完，回看整轮证据，把两样东西写进**经验库**：

1. 采用过的**完整 harness**（可执行，不是摘要）
2. `EXPERIENCE.md`：为什么选它、它修了哪个反复出现的弱点、什么情况下适用

**然后下一个任务，仍然从最原始的基础 harness 出发**，只带经验库。

### 为什么不能直接继承上一轮调好的 harness

论文做了反向对照，这是全篇最有价值的**负结果**：

| 做法 | Code | Web |
|---|---|---|
| 基础 harness（不改进） | 73.4 | 69.9 |
| **直接拿上一轮 harness 往下滚** | **63.2** ↓10.2 | **65.0** ↓4.9 |
| 带经验库（k=1 攒的） | 回到基线 | 回到基线 |
| 带经验库（k=5 攒的） | +0.9 | +4.4 |

**结论**：为单个任务过度定制的 harness，直接继承会把噪声放大成退化。**「为上一题调好的东西」不是资产，是污染。**

正确做法：**传「什么时候该信什么」，不传「成品」。**

### 消融：三个组件各值多少

| 去掉什么 | WorkBuddy | JobBench |
|---|---|---|
| 完整版 | 77.5 | 36.0 |
| 去掉经验库 | −3.1 | −1.8 |
| **去掉两个编辑器的视角切分** | **−2.9** | **−3.7** |
| 去掉 Compose | −1.6 | −1.9 |

**第二强的是视角切分。** 这条最反直觉：让「通用行为」和「领域知识」两个角色各写一版，比让一个角色写得好**更有用**。

原因很朴素：**同一个 prompt 写不出两种互相矛盾的假设。** 你要它同时想「这属于通用毛病」和「这属于本行知识」，它会挑一个，另一个就丢了。

## 四、可搬运的七条

> 判据：**能不能脱离 Harness² 的代码和环境，单独用？** 下面每条都能。

### 1. 优化对象选「可 diff 的外壳」，不是权重
改文件 = 改能力，每次改动是 diff → 可审计、可回滚、可归因。
**落地**：把提示词/护栏/技能当**有版本的文件树**，一处改动一处 diff。别塞进一个巨型 config。

### 2. 没有标准答案时，监督信号用「因果对比」，不用「价值判断」
同任务同环境跑两遍，问「这改动动到目标行为了吗」。
**边界**：只能证伪。必须另配结果验收。

### 3. 视角切分优于「让写手更强」
**落地判据**：如果你发现自己在同一个文件里同时维护「通用做法」和「本行知识」→ 拆开。它们会互相挤掉。

### 4. 不传成品，传经验
**落地**：任务结束时**别**继承「这轮调好的那套」，写「为什么这么调、修了哪个反复出现的毛病、什么情况下适用」。
**同构**：跟本工作区 `AGENTS.md` 的寿命列是同一个结构 —— 登记表只留一句话 + 指路，不复述内容，到期标黄提醒「用前先验证」。

### 5. 经验条目三段式，且证据不足就不写
`改动 → 目标行为 → 后果` + `适用条件`。
**空经验库胜过假经验**：写错比不写更贵，因为假经验会被复用。

### 6. 归因要防「预算当质量」
任何「我优化后涨了 X」，先问：**几步？几次？花了多少？**
k 从 1 到 5 只涨约 3 分，却要多付约 10 倍 rollout。**单步增益才是可归因的。**

### 7. 执行侧和改善侧分两本账
它的执行侧确实变好了（步数 25.4→21.9，工具错误率 JobBench 14.4%→9.1%），这是硬的。
但改善侧成本没给美元数，社区已在 Issue #4 要求加 `--max-usd`。
**落地**：efficiency（步数/错误率/耗时）和 search 成本（token/$）分开记，后者**必须能设上限**。

## 五、不该抄的（读这类论文的五个判别问题）

这套模式现在会被反复复现，五问比结论本身耐用：

| # | 问什么 | Harness² 的答案 |
|---|---|---|
| 1 | 宣称分数是**最大值**还是平均值？ | 最大值。+11.5 出在最弱执行器（GLM-5 64.2）上；强模型只有 +5.1 |
| 2 | **评委和选手是同一个**吗？ | 是。提议、合成、选优全是一个模型；失败案例里 95 分被 55 分挤掉 |
| 3 | 提升来自**方法**还是「多试几次」？ | 部分。单步才是可归因部分；执行侧确实变短了 |
| 4 | **监督通道堵住**了吗？ | 没堵。要求使用者自己配网络限制，默认执行器不设限 |
| 5 | 基准和数据**谁出的、锁版本了吗**？ | 三个基准两个出自关联方；数据没锁 commit，`seed` 只打乱顺序 |

**第 4、5 条是通用杀器**：只要「不许看答案」这道门靠使用者自觉关，报告的任何分数都带一个消不掉的问号。

## 六、怎么用到自己身上

### 已落地（2026-10-20）

`~/.dsh/prompt-inject.md` 按第 3 条拆成两层：

| 层 | 内容 | 过期方式 |
|---|---|---|
| 一、不变式层 | 怎么工作：铁律、性格、交付纪律、思考预算、自检 | 几乎不变 |
| 二、领域层 | 这台机器、这个人具体什么情况 | 外部一变就过期 |

**判据一句话**：把这句话挪到一个完全不相干的陌生任务上，它还成立吗？成立 → 不变式层。

⚠️ 一个机制约束（查源码确认，不是猜的）：`readPromptInjectFileSync` **只读 `$DSH_HOME/prompt-inject.md` 一个路径**。所以第二层不能是独立的同级文件 —— 那样它根本不进上下文。拆的是**同一文件内的显式分节**，不是物理文件。

### 还没做

拿一个自己的任务集做 **k=1 单步实验**：把 harness 当目录做 diff，同任务跑两遍，看「行为对比」能不能在自己的弱模型环境里复现增益。
跑不出来 → 它的增益高度依赖那个特定强编辑器，那就更值得记下来。

### 别整套搬

Linux-only + Vertex AI + Docker + Pandoc，成本和本机条件都不匹配。真要在 Windows 上试，先过两个**静默**坑：
`harness2/core/schedule.py` 直接 `import fcntl`（启动即 `ModuleNotFoundError`）；`read_tree` 用 `str(path.relative_to(d))` 当键，Windows 下产出反斜杠，而下游全假设正斜杠 → **每一次提议的编辑都被静默拒绝**，不报错。
