# Thariq · 未知地图

> 来源两处，都是 Thariq Shihipar（Anthropic，Claude Code 团队）：
> ① **A Field Guide to Fable**，AI Engineer World's Fair 2026 演讲，19 分 28 秒，https://ai.engineer/talks/9fubhllmsBU-field-guide-to-fable
> ② **The unreasonable effectiveness of HTML**，配套 20 个示例页：https://thariqs.github.io/html-effectiveness/
> **这篇是四篇里方法最硬的一篇**，因为它把「我怎么知道自己没说什么」变成了可以分类、可以逐个处理的东西。

## 一、能力悬垂（capability overhang）

他的起点：模型靠数据、反馈、算力训练出来，但**它实际表现还取决于外面那层 harness（外壳）和提示词**。那些东西编码了「我们当下对这个模型的理解」，所以它们会**限制模型能干什么**。

他把「潜在能力」和「能被用出来的能力」之间的落差叫 **capability overhang**。

**他给的例子很具体**：纯聊天模型回答「宝可梦名字里以 AW 结尾的有哪些」很吃力。Claude Code 能去抓全部名字、写个脚本、过滤出结果。

关键不是「模型记性好」，是**工具让它能取证、能跑可靠流程**。

同样的道理适用于写代码：不要假设「得有个能装下整个代码库的上下文窗口才能干活」。它可以自己用 bash 去搜、去拼出工作上下文。

**对老大的意义**：这一条解释了为什么「同一句话，有的 AI 答得好，有的答得烂」。差别常常不在模型，在**外面那层有没有给它工具和数据**。

## 二、harness 要跟着模型变（有一个大坑）

Claude Code 团队**砍掉了 80% 的 system prompt**。

他描述了一个循环：早期小提示词 + 少工具 → 后来大提示词 + 大量指令和例子 → 现在又回到小提示词。

理由是：**对新一代模型，例子会收窄解的空间**，因为模型可能比给的例子更有想象力。他的建议是**给上下文，别给过多约束**，也别留一堆「老模型才需要的」一刀切禁止项。

他还说了一句方法论上很重要的话：**这件事更像生物学，不像物理学**。经验性的、有机的，有有用的直觉但没有完整规则。所以别指望存在一套永久的提示词公式。

### ⚠️ 这条不能直接搬去改本机

本机的 `~/.dsh/prompt-inject.md` 里那些约束（中文 stdout 要 reconfigure、junction 只能怎么删、定位先于扫描）**是踩坑换来的**，不是「老模型习惯」。

Thariq 砍的是**面向通用编码任务的指令和例子**，不是**记录本机真实破坏性事实的护栏**。要删也得先测。

## 三、地图不是疆域：四种「不知道」

这是他最有用的贡献。

**地图** = 你心里的提示词、计划、规格。**疆域** = 真实的代码库和它的约束。

**每一个「地图没描述、但疆域里出现了岔路」的地方，就是一个未知。**

他有个反直觉的补充：**模型越强，遇到的这种岔路越多**，因为它能走更大的问题空间。所以「模型更强了就不需要写清楚」是错的，恰好相反。

四种拆法：

| 类型 | 定义 | 怎么处理 |
|---|---|---|
| **已知的已知**（known knowns） | 一般已经写在提示词里 | 不用管 |
| **已知的未知**（known unknowns） | 你意识到但还没解决的问题 | 让模型**面试你** |
| **未知的已知**（unknown knowns） | 太显然所以不会写下来的假设或偏好 | 做**对照原型**逼出来 |
| **未知的未知**（unknown unknowns） | 压根没进过你脑子的考虑 | 做**盲区扫描** |

**这个框架把瓶颈从「写出代码」挪到了「识别出哪些决定模型无法从不完整的规格里安全推断」。**

### 三个对应技法

**1. 盲区扫描（blind spot pass）**

在跟不熟的模块打交道之前（他的例子是个认证服务商），让模型去读相关模块和可用的上下文来源（git diff、Slack），报出反复出现的坑和你缺的知识。

他说这招**不只用于软件**：他学视频调色也是这么学的。

**2. 对照原型（brainstorms and prototypes）**

对那些「能认出来但说不清」的偏好：让模型做一个 HTML 页面，并排给你四种差别很大的仪表盘设计方向，你指着其中一个说「像这个」。

**机制不是模型神奇地知道你想要什么，是它把模糊的偏好变成具体可指的反馈。**

**3. 面试（interview）**

让模型一次问一个问题，**按「改动影响架构的大小」排序**，然后回你一张决策表和一段可直接粘贴的实施提示词。

（他讲的演进有意思：Opus 4 连可靠调用这个工具都做不到，Opus 4.5 能面试用户，Opus 4.8 / Fable 能直接生成带嵌入问题的 HTML 报告。）

## 四、实现中别失联

三条，都在讲「你怎么保证自己还在环里」：

**实施笔记（implementation notes）**：让它每次遇到未知就记一笔。这些笔记暴露了「工作在哪里偏离了原来的地图」，以及**为什么偏离**。记录不消除不确定性，但让关键判断对人可见。

**给参照物，别只给文字规格**：现成代码能表达意图，哪怕它来自另一套系统或另一种语言；HTML 稿可以当 React 组件的参照。

**事后考你（quiz）**：让模型反过来出题考人。**答错的地方指回你跳过的章节。** 他的原话逻辑是：代码写完了不等于你懂了，而 PR 是要你去讲、去合并的。

## 五、HTML 那条线（第二篇来源）

他的另一篇主张：**要 Claude 输出的时候，用 HTML 而不是 Markdown。**

他攒了 20 个例子，每个都是一个自包含 `.html`，按「它替代掉什么工作」分组：

| 类别 | 例子 |
|---|---|
| 探索与计划 | 三条技术路线并排对比、四种视觉方向渲染出来给你指、带时间线和风险表的实施计划 |
| 代码评审 | 带边注和严重度标签的 diff、给评审者写的 PR 说明、模块图（框和箭头，热路径高亮） |
| 设计 | 设计系统变成色板、一个组件的全部状态铺在一张图上 |
| 原型 | 带时长和缓动滑块的动画沙盒、四屏可点击流程 |
| 图解 | 内联 SVG 插图、可点击的部署流程流程图 |
| 报告 | 周报、带分钟级时间线的事故复盘 |
| 自定义编辑器 | 拖拽分诊板、功能开关编辑器（带「复制 diff」按钮）、提示词调参器 |

**他反复强调的一点**：自定义编辑器**一定要有个导出按钮**，把你在界面上做的东西变回能粘回给模型或能提交的东西。「你留在环里，环收得更紧。」

**为什么这条对老大有用**：本机 DSH 有 `render_canvas` / `render_ui` 这些工具，正好是这个路子。要对比方案的时候，让模型做一页并排的，比读三段文字快得多。

## 六、最后那节：承认失去

他专门留了时间讲这个，挺罕见的：

回到他以前做的一家创业公司，当时必须在「应用变快」和「加新功能」之间选，因为实现要几个月。用新工具重看那个代码库，**他以为要几周的东西几小时就做完了**。同时他也感到失落：手工写代码、脑子里装着整个代码库，这种感觉在变。

他的结论不是否认这种失落，也不是宣称 agentic coding 解决了所有问题。他的最终建议是：**对继承来的假设要「不那么讲道理」**（be less reasonable）。别一上来就接受熟悉的那种取舍，去测一下更好的工具是不是能让多个目标同时成立，让真正的约束自己暴露出来。

**但他划了一条线，这条最容易被忽略：**

> However, faster implementation is not the same as a successful product or meaningful impact.
> （然而，更快的实现不等于成功的产品或有意义的影响。）

他明确区分「更容易构建」和「产生价值」，后者仍然很难，仍然要反复试很多次。

## 哪里存疑

> 我的判断。

**1. 「砍掉 80% system prompt」的数据我只从演讲转述里看到，没看到原始实验记录。** 转述站（ai.engineer）是官方 talk 页面整理的，可信度较高，但「80%」这个数字怎么算的、砍掉前后测了什么，演讲里没展开。

**2. 四分法（known knowns 那套）原本是心理学/决策论里的老概念**（拉姆斯菲尔德 2002 年那次发言让它出圈），Thariq 的贡献是把它套到「写规格」这件事上并给了对应技法。不是他原创的框架，别当成新理论。

**3. HTML 那篇的 20 个示例我没逐个打开验证。** 我看了页面结构和描述文字，示例本身是 20 个独立 html 文件。要学具体写法得自己点开看。
