# 上下文工程入门：里面有什么、怎么管、能不能模块化

> 写给刚开始碰 agent 的人（也就是老大自己）。四个问题按顺序回答：
> ① 上下文包括什么 ② 各自有什么用 ③ 管理方式有哪些 ④ 能不能模块化。
>
> 材料来自四篇，都读了正文：
> - **Anthropic**《Effective context engineering for AI agents》
>   https://www.anthropic.com/research/effective-context-engineering-for-ai-agents

## 零、先用一句话说清上下文是什么

**上下文 = 这一次调用模型时，你喂给它的全部 token 序列。**

模型没有记忆，没有状态，没有「上次会话」。它每次被调用，只看得到这一次塞进去的东西，看完就丢。所以「上下文」不是模型的脑子，是**它这一次的工作台**。

工具调用、多轮对话、agent 循环，全是同一种做法的重复：把累积的东西重新拼成一个序列再喂进去。

一句常见的类比：模型是 CPU，上下文窗口是内存（RAM）。这个类比有用，但要看住它的边界：**内存里的东西可以按地址随机访问，上下文不行。** 上下文里的位置会影响模型的注意力分配（后面讲）。

## 一、上下文里到底有几样东西

按一次调用的组装顺序，从上到下：

| 序号 | 组成 | 谁放进去的 | 一次能占多少 |
|---|---|---|---|
| 1 | 系统提示 / 系统指令 | 开发者写死 | 几百到几千 token |
| 2 | 工具定义（名称、描述、参数 schema） | 开发者配置 | 每个工具几十到几百 token，工具多了爆 |
| 3 | 少样本示例 | 开发者放 | 按示例条数 |
| 4 | 检索到的材料 | 检索代码放 | 变量，最容易失控 |
| 5 | 长期记忆 | 记忆系统放 | 变量 |
| 6 | 对话历史 | 累积 | 随轮次线性涨 |
| 7 | 工具调用结果 | 累积 | 常常是全部里最大的一块 |
| 8 | 当前用户输入 | 用户放 | 几十到几千 |
| 9 | 输出预留空间 | 服务配置 | 必须留，不然答到一半被截断 |

**注意 9 号。** 上下文窗口指的是一次调用能处理的**总数**，输入加输出。窗口 200K 的意思不是「能塞 200K 输入」，是「输入加输出加一起不超过 200K」。很多人只算输入，结果长回答被截断，误以为是模型不行。

**再注意一个容易搞混的区分**：

| 概念 | 是什么 | 是不是上下文 |
|---|---|---|
| 上下文 | 这次调用输入的 token 序列 | 是 |
| KV cache | 模型算这些 token 时缓存下来的中间结果 | 不是，但由它派生 |
| 模型权重 | 训练学的参数 | 不是，所有调用共享 |

这个区分有用，因为「缓存命中」讲的是 KV cache，不是上下文。同一段文字第二次出现时算得快，是因为 KV cache 还能用，跟上下文长度没有直接关系。

## 二、每一块各自有什么用，坏了会怎样

这是初学者最该建立的手感：**不是「塞得多就好」，每一样都有自己的失败方式。**

### 1. 系统提示：定角色、边界、输出形状

作用：告诉模型「你是谁、什么不能做、结果长什么样」。
Anthropic 给了一条很好的判据，叫**「合适的高度」**：

- 太低：把 if-else 式的复杂逻辑硬写进提示里。脆、难维护，改一个条件整段都要动。
- 太高：写成「你要专业、要严谨」这种空话。模型拿不到具体信号，只能猜。
- 合适：具体到能引导行为，又留足够的判断空间。

他们还建议**分段组织**：用 `<background_information>`、`<instructions>`、`## Tool guidance`、`## Output description` 这种标记切开，而不是一大段散文。

**失败长什么样**：指令和模型默认行为打架（Sourcegraph 的说法是「矛盾，不是长度」）。症状会在三步之后才暴露，所以特别难查。

### 2. 工具定义：告诉模型「能做什么、怎么调」

作用：工具是模型跟外部世界之间唯一的接口。没有工具，模型只能用训练时记住的东西回答。
**代价被严重低估**：每个工具的 JSON schema 每次调用都占着窗口。工具一多，光是「有哪些工具」就吃掉几千 token。

**失败长什么样**：工具集臃肿、功能重叠，模型在「差不多一样的两个工具」之间反复犹豫。Anthropic 和 Sourcegraph 说同一句话：**如果人类工程师都说不清这个场景该用哪个工具，别指望模型能说清。**

有一个缓解手段叫**延迟加载**：先只给工具名字，模型需要时再拉完整 schema。这只省了第一笔账（定义），省不了第二笔（每次调用返回的结果）。

### 3. 少样本示例：用「图片」代替解释

作用：一个例子抵一千字说明。Anthropic 的原话是 examples 是 worth a thousand words 的「图片」。

**失败长什么样**：为了覆盖所有边界情况，往提示里堆一长串特例。他们明确不建议这么做。**要好例子，不要多例子**：挑几个有代表性、覆盖不同形态的典型例子，胜过二十个只差一点点的边界例子。

### 4. 检索到的材料：把外部知识搬进来

作用：模型不知道你公司的制度、你的代码、昨天的新闻。检索补这块。
两种做法，值得分清：

| 做法 | 什么时候拿 | 优点 | 缺点 |
|---|---|---|---|
| **预检索**（embedding 向量检索为主） | 调用之前，一次性算好 | 快 | 材料可能已经过期，切的块可能不对 |
| **即时检索**（just in time） | 跑到需要时，模型自己调工具去读 | 永远是最新的，能逐层展开 | 慢，要靠模型会搜 |

即时检索的核心是**只保存轻量标识**（文件路径、查询语句、链接），需要时再加载内容。Anthropic 举的例子是 Claude Code 分析大数据库：模型写针对性查询、存结果、用 `head`/`tail` 看片段，从不把整个数据集读进上下文。

**失败长什么样**：把无关材料也塞进去。Sourcegraph 的实测结论很硬：**加无关上下文会让质量变差，不是持平。** 另外还有个更隐蔽的失效：检索层做好了，模型不用（他们的跑批里，关键词搜索 4813 次，语义检索 587 次，深度检索 602 次里只用了 6 次）。**模型忽略的检索层等于没建。**

### 5. 长期记忆：跨会话的那部分

作用：让下一次不必从零开始。分两类，别混：

| 类型 | 是什么 | 例子 |
|---|---|---|
| **短期 / 工作记忆** | 这次任务里的上下文 | 这一轮的对话、工具调用记录 |
| **长期记忆** | 跨会话保留的约定和决定 | 项目规范、上次定的方案 |

LangChain 把长期记忆再分三种，这个分法好用：**情节记忆**（做过什么、要什么例子）、**程序记忆**（该怎么做的指令）、**语义记忆**（事实）。

**失败长什么样**：Sourcegraph 指出最被低估的一种是**失效（invalidation）**。一条长期记忆写着「认证服务用 JWT」，可团队六周前就换掉了。这种记忆**比没有记忆更糟**，因为模型会拿着一个自信的错误前提做决定。

### 6. 对话历史：累积的那部分

作用：让模型知道刚才发生了什么。
**失败长什么样**：越长越不可靠。这是下面第三节的主题。

### 7. 工具调用结果：往往最大，往往最该删

作用：模型看命令输出、看文件内容、看接口返回。
**关键认识**：**这是上下文增长的主要来源，也是最安全的第一刀。** Anthropic 说得很直白：一个工具在很久以前调用过，模型为什么还需要看它的原始输出？

## 三、为什么「窗口大就多塞」是错的

三条实证，按硬度排：

**1. Context rot（上下文腐坏）。** Chroma 测了 18 个模型，结论是模型**不会均匀地使用上下文**，输入越长，表现越不可靠。注意措辞：这是模型行为的事实，不是厂商调大窗口就能修掉的限制。

**2. 注意力预算是有限的。** Transformer 让每个 token 关注其它所有 token，n 个 token 产生 n² 对关系。位置越靠后，生成成本越高（NVIDIA 那篇实测：256K 相比 16K，生成一个 token 贵 3.6 到 7 倍）。更根本的是，模型见过的长序列比短序列少，长距离依赖的专门参数也少。

Anthropic 的落点：**上下文是一份有限资源，边际收益递减。** 每加一个 token 都在消耗这份预算。

**3. Lost in the middle（中间失明）。** Liu 等人 2023 年的发现：相关信息出现在**开头或结尾**时表现最好，埋在**中间**时明显下降，连明确的长上下文模型也一样。

**这条有个直接的工程后果**：**组装顺序是设计决策，不是偶然。** 最高价值的材料放头或尾，不要埋在一堆检索块中间。

**一句话总结**：窗口变大只是把失败方式从「截断」换成了「稀释」。

## 四、管理方式有哪些

三套分类，说法不同，指的是一件事。先给对照：

| 你在做什么 | LangChain 的叫法 | Anthropic 的叫法 | Sourcegraph 的叫法 |
|---|---|---|---|
| 把信息存到窗口外 | **Write** | 结构化笔记 | Memory 支柱 |
| 把需要的信息拿进来 | **Select** | 即时检索 / 渐进展开 | Retrieval 支柱 |
| 把窗口内变短 | **Compress** | 压缩（compaction） | Compaction |
| 让不同任务不共享窗口 | **Isolate** | 子代理架构 | 子代理 |

### Write：写到窗口外面

**草稿纸（scratchpad）**：把计划、进度写到文件或状态对象里。Anthropic 的多代理研究系统里，主研究员第一件事就是把计划写进 Memory，理由很实在：窗口超了 20 万 token 会被截断，计划必须留下来。

**记忆**：跨会话的持久化。ChatGPT、Cursor、Windsurf 都做了自动生成长期记忆。

### Select：按需拿进来

预检索还是即时检索，上面第一节讲过了。这里补一条 Anthropic 的说法：**渐进展开（progressive disclosure）**。模型通过探索逐层获取信息，文件大小暗示复杂度、命名习惯暗示用途、时间戳暗示相关性。它像人一样，不是背下整个图书馆，而是建一套索引，需要时去查。

### Compress：压短

**压缩（compaction）**：快满时把对话总结掉，用摘要开一个新窗口。

Anthropic 在 Claude Code 里的实现值得抄：保留架构决策、未解决的 bug、实现细节，丢掉冗余的工具输出，然后带着摘要加**最近访问的五个文件**继续。

**Sourcegraph 给了一个能直接用的压缩提示词**，比「请总结一下」强得多：

```
把这个会话压缩成能开启新窗口的种子。必须保留：
1. 任务陈述原文
2. 已经看过的文件路径，以及每个里面有什么
3. 做过的决定，以及每个决定的理由
4. 试过并失败的方案，以及为什么失败
其余都可以丢。
```

他们补了一句关键的话：**漏掉第 4 条，新窗口会兴高采烈地把失败方案再试一遍。**

**最轻的一刀是清工具结果**：只删工具调用返回的原始内容，不动其它。Anthropic 把它叫「最安全最轻的压缩」。

### Isolate：隔开

**子代理**：主代理拿高层计划，子代理用干净的窗口做具体的深活。子代理可能烧掉几万 token，只回一段一千到两千 token 的摘要。

好处是关注点分离，代价是协调成本。而且 Sourcegraph 提醒了一个坑：**检索做得烂的子代理，照样会给你一个信誓旦旦的摘要。**

Anthropic 还给了选型判据，我觉得是这几篇里最实用的一句话：

| 你的任务长什么样 | 用哪招 |
|---|---|
| 大量来回，需要保持对话连贯 | 压缩 |
| 迭代开发，有清晰里程碑 | 记笔记 |
| 复杂研究分析，并行探索有收益 | 子代理 |

### 顺带一个 2026 年的新标签：意图工程

Sourcegraph 提到 **intent engineering（意图工程）**：上下文工程决定「它该知道什么」，意图工程决定「它该想干什么」，包括什么算「做完」、可以牺牲什么。

他们给了一个真实的调试故事：告知 agent 有哪些工具的那段前言改了五版。前两版太含蓄，模型无视工具；第三版用全大写强调，采用率到 90%，但模型开始反复重试失败的查询；第四版退回软引导，掉到 40%。**检索层一直没动，改变结果的只有那段意图陈述。**

判据：**检索已经不错、agent 还是乱转，先检查你让它想要什么，别急着重建管线。**

## 五、上下文可以模块化吗

这是四个问题里唯一没有标准答案的。我给一个分层的回答。

### 先说是的，它就是模块化的

今天所有工程实践都建立在这个前提上，而且是在三个层次上：

**层次一：来源模块。** Sourcegraph 的四支柱（指令 / 检索 / 记忆 / 工具）就是四个可独立实现的模块。Switch 掉检索层不影响记忆层，换掉记忆后端不影响工具定义。

**层次二：协议模块。** MCP（Model Context Protocol，模型调用外部工具的标准协议）把外部能力标准化成三类：**resources**（给用户或模型的数据）、**prompts**（模板化的工作流）、**tools**（模型能执行的函数）。一个 MCP server 就是一个可插拔模块。

**层次三：策略模块。** Write / Select / Compress / Isolate 是四种独立的动作，可以自由组合。压缩策略可以换，检索策略可以换，互不影响。

**所以对第一个层次的回答是：可以，而且必须模块化，否则没法维护。**

### 但要加三条边界，不然会翻车

**边界一：模块化的是「来源」，不是「注意力里的相互作用」。**

你把检索结果和记忆拼进同一个窗口之后，它们之间的关系是 n² 的，不是相加的。两块单独看都对，一起放进去可能互相干扰。这就是 **context clash**（上下文冲突）：两个来源互相矛盾，而窗口里没有任何东西能裁决。

**模块之间可以有清晰的边界，注意力没有。**

**边界二：模块化不等于可替换。**

工具有个很具体的耦合例子：功能重叠的工具会让模型选错。所以「加一个工具模块」不是零成本，它会改变其它工具被选中的概率。Sourcegraph 的数据也支持这点：工具给多了，有时效果更差，原因是没告诉模型什么时候用哪个。

**边界三：预算是一份共享资源，所以不能各模块独立调优。**

窗口的总预算是固定的。检索想要 10K，记忆想要 5K，工具定义想要 8K，系统提示想要 3K，加起来超了怎么办？**这是一个全局配比问题**，任何一个模块单独把自己的内容调到最优，都可能挤掉别人更重要的内容。

### 我的结论

**上下文可以按模块组织和实现，不能按模块独立优化。**

- **能干净模块化的**：存储（文件、数据库）、外部能力（工具、MCP server）、跨会话记忆、离线预处理的索引。这些的接口清楚，替换成本低。
- **半模块化的**：压缩策略（换策略会影响任务表现，但接口清楚）、子代理（边界清楚，但摘要质量决定成败）。
- **不能模块化的**：窗口内的排布顺序、各模块的 token 配比、以及「哪些内容互相冲突」。这三件事只能在**拼装那一刻**整体判断。

一句话：**模块负责「造零件」，拼装负责「装成一辆车」。把零件做到最好，不等于车能跑。**

### 一张判据表（以后自己判断用）

| 你想做的事 | 能不能模块化做 | 判据 |
|---|---|---|
| 换一个检索源 | 能 | 接口固定，只换实现 |
| 加一个工具 | 半能 | 先查它跟现有工具是否功能重叠 |
| 换记忆后端 | 能 | 记忆的读写接口不变就行 |
| 改压缩提示词 | 能，但要重测 | 压缩会丢信息，必须跑一遍任务看掉多少 |
| 调整各块的 token 比例 | 不能 | 全局决策，只能整体试 |
| 决定材料放窗口哪一段 | 不能 | 位置效应，必须看整体顺序 |

## 六、落到老大身上

**1. 他已经在做这件事，而且比大部分教程写得细。**
`prompt-inject.md` 是系统指令模块（常驻）；`fact-wiki` 和 obelisk 是检索模块（按需）；`digests` 和 `active-prefs` 是记忆模块（压缩后的状态）；skill 描述是工具定义模块（每个 description 都在占预算，这就是为什么他要求 ≤480 字）。

**2. 他现在的结构里，最缺的是「配比」这一层。**
每个模块都在自己长，但没有一个地方说「常驻预算多少、按需检索多少」。NVIDIA 那篇给的参照是 **7 到 9K token 的中位峰值**。他的常驻注入已经是这个量级的几倍。**加一条预算上限，比再加一个模块有用。**

**3. 有一个动作现在就能做：把「完成判据」写进压缩。**
Sourcegraph 那句「漏掉第 4 条，新窗口会把失败方案再试一遍」和 NVIDIA 附录 A 的「完成判据清单」是同一件事的两个说法。他的 `PROGRESS.md` 有目标行，digest 里没有。**这就是他那套系统里最该补的一个字段。**

**4. 一个反直觉的提醒。**
这四篇文章没有一篇说「做得越多越好」。Sourcegraph 的原话是：上下文工程是一门**减法**的纪律，几乎所有技术都在移除 token，而不是添加 token。**他习惯做加法（加模块、加规则、加项目），这条值得贴在墙上。**

## 六点五、本机 DSH 是怎么压的（大白话版）

这一节不讲别人的文章，讲**你现在正在用的这个软件**。来源两处：拆开 DSH 的安装包读它的实现文档，再解压会话日志数真实记录。

### 四块零件，各干一件事

DSH 的压缩不是一个总开关，是四块可以拆装的零件：

| 零件 | 干的活 | 要不要叫模型 |
|---|---|---|
| `compaction-basic` | 判断该不该压、挑哪一段、叫模型写摘要 | 要 |
| `tool-result-pruner` | 把超长的工具输出掐头去尾 | **不要** |
| `image-offload` | 图太多装不下时，把旧图换成一行文字说明 | 不要 |
| `command-compact` | 提供 `/compact` 让你手动压 | 要 |

**顺序很关键：先剪枝，剪完够用就不写摘要了。**

什么意思？假设一次压缩要腾出 3 万 token 空间。剪枝直接把最占地方的几个工具输出砍掉，可能就够了，那就不用再花钱叫一次模型写摘要。**便宜的手段先上，贵的留作后手。**

### 什么时候触发

先说清三个数，它们决定「多大的对话才会被压」：

| 数 | 本机现在是多少 | 是什么意思 |
|---|---|---|
| **窗口** | 131,000 | 模型一次最多能看多少 token |
| **留给回答** | 8,192 | 必须空出来的空间，不然话说到一半被切断 |
| **安全余量** | 65,536 | 故意留的缓冲，怕估得不准 |

规则是**两个条件取小的那个**：

- 条件一：窗口的 80%，也就是 131,000 × 0.8 = 104,800
- 条件二：窗口减回答减余量，也就是 131,000 − 8,192 − 65,536 = 57,272
- 取小的：**57,272 就触发压缩**

触发之后，**最近的 19,649 token 逐字保留不动**（算法是「窗口减回答」的 16%），剩下的约 37,000 token 历史会被换成一条摘要。

**举个你会遇到的场景**：你让我整理文章，我抓一篇 NVIDIA 正文就吃掉 8,000 token，抓五篇就是 40,000。再加读笔记、写文件、工具返回，一场会话攒到 57,272 只是时间问题。到那一刻，前面三万七千左右的历史会变成一个几百字的摘要，中间的细节全没。

**最容易算错的地方**：很多人以为「窗口的 80% 就是阈值」，把 104,800 当答案。实际被「安全余量」那一项压到了 57,272。窗口越小的模型，这个余量占比越大，128K 窗口下阈值只有窗口的 44%。

### 压缩一次，具体发生五步

1. **量一下**：模型真正开始干活之前，先算「这次请求总共多少 token」。超了 57,272 就进下一步。
2. **先剪**：每个超过 8,192 个字符的工具返回，只保留开头 4,096 个和结尾 1,024 个，中间写一句 `middle pruned`（中间被剪掉了）。原始内容还在日志里，随时能查，只是模型看不到了。
3. **再总结**：还剩超，就叫一次模型写摘要。输出最多 65,536 token，**只收它写的文字**，它的思考过程和工具调用全丢掉。
4. **换掉**：最旧的那一段被**一条消息替换**，内容是 `<compacted-summary>` 开头的摘要。注意是替换，不是追加在后面。所以历史长度是真的变短了。
5. **重算缓存**：模型跑的时候会把算过的内容缓存起来（叫 KV cache，好比草稿纸上算过的步骤）。因为前面那段被换成了别的内容，**从换了的地方往后，缓存全部作废要重算**。换之前的部分还能用。

### 有四样东西压不掉

| 压不掉的 | 为什么 |
|---|---|
| 系统提示（我的性格文件、你的工作区约定） | 它在窗口最开头，被设计成永远不动 |
| 工具定义 | 同上，属于常驻部分 |
| 会话开头那条 | 属于前缀，不在可压缩范围 |
| 一次特别大的工具调用 | 它是一个整块，拆不开，只能整个留或整个丢 |

**这条结论很重要**：压缩只能救「聊天记录」，救不了「常驻成本」。你的 `prompt-inject.md` 加上各层 `AGENTS.md` 每一轮都占着位置，压缩管不到它们。**想让常驻变小，只能自己去删文件，没有自动机制。**

### 摘要里必须写什么

DSH 内嵌了一条固定指令，要求摘要按八个小节写，一段都不许缺，空的也要写「(none)」：

| 小节 | 要写什么 |
|---|---|
| 1. 原始请求与意图 | 你最初要什么、后来又改了什么，重要处要原文引用 |
| 2. 关键技术概念 | 用到的技术、框架、约定 |
| 3. 文件与代码 | 精确路径，以及这个文件为什么重要 |
| 4. 报错与修复 | 什么错了、怎么解决的、你当时怎么反馈的 |
| 5. 待办 | 明确要求了但还没做完的 |
| 6. 当前进度 | 压缩这一刻正在做什么 |
| 7. 下一步 | 只写一个动作 |
| 8. 关键上下文 | 做过的决定和理由、约束、你的偏好、待解的问题 |

外加几条规矩：路径、命令、报错原文、数值必须原样保留；你的指正必须忠实记下；不许提「这是一次压缩」；**前面已有旧摘要时不许照抄，要把新旧合并成一份**。

这套结构跟昨天那篇 NVIDIA 论文附录 A 的三条几乎一样：任务原文、当前意图、与未来执行相关的产物。**不同团队最后都收敛到同一个写法，说明这几项是真正不能丢的。**

### 什么时候不等它自动压

- **`/compact`**：在输入框敲这个，立刻压一次，不用等攒到 57,272。如果我这轮还在干活、或者压缩正在跑，它会回「暂不可用」，你发的消息排队等压缩完再生效。
- **溢出兜底**：万一估算不准真的超了，模型那边会报「窗口超了」。DSH 收到后**不看阈值，直接砍最大的一刀**，然后重试一次。只重试一次，再超就真的失败。

### 这套东西的四个弱点

1. **token 是估出来的**。拿不到真实用量时按「4 个字符算 1 个 token」估，**中文估得偏低**。所以中文长会话可能已经超了才被发现。
2. **整块的压不掉**。一次返回几万字的工具调用不能切一半，要么留要么丢。
3. **摘要本身有上限**，而且模型的隐藏思考也会吃掉这个额度，所以摘要可能被截断。
4. **摘要失败不会倒退**。它记一条警告，然后带着超标的历史继续跑。这时候你看到的就是「它好像有点糊涂」。

### 本机真实数据（解开最近 25 个会话数出来的）

| 事件                   | 次数     | 意思               |
| -------------------- | ------ | ---------------- |
| `compaction/start`   | 8      | 压缩启动了 8 次        |
| `compaction/summary` | **3**  | 其中只有 3 次真叫模型写了摘要 |
| `compaction/prune`   | **33** | 剪枝剪了 33 回        |
| `compaction/end`     | 8      | 8 次都正常收尾         |
| `image/offload`      | 0      | 没处理过图片超预算        |

8 次压缩里 5 次是剪枝就解决了，没花钱叫模型写摘要。33 次剪枝比 8 次压缩多，因为一次压缩会挨个剪好几个超大的工具输出。

**你这台机器上，压缩的主力是剪枝，摘要只是兜底。**

这也解释了一个你可能遇到过的现象：**感觉它「忘了前面查到的东西」，多半不是摘要写坏了，是那些工具输出早就被剪掉了。** 原文还在日志里，随时能查，但当时那几轮它确实看不到。

## 七、术语速查

| 词 | 一句话 |
|---|---|
| 上下文 | 一次调用喂给模型的全部 token |
| 上下文窗口 | 一次调用能处理的总 token 数，输入加输出 |
| KV cache | 算过的 token 的中间结果缓存，命中就快 |
| 注意力预算 | 上下文越长，能分给每个 token 的注意力越少 |
| context rot | 上下文变长，召回和推理可靠性下降 |
| lost in the middle | 信息埋在长上下文中间时最难被用上 |
| compaction | 把快满的上下文总结成摘要，开新窗口 |
| scratchpad | 写到窗口外的草稿，存计划和进度 |
| 即时检索 | 只存标识，需要时用工具去读内容 |
| MCP | 模型调外部工具的标准协议（resources / prompts / tools） |
| context poisoning / distraction / confusion / clash | 污染（假事实进了窗口）/ 分心（无关材料挤掉相关）/ 混乱（多余内容影响回答）/ 冲突（两块材料互相矛盾） |
| 意图工程 | 规定它该想要什么、什么算做完 |
