# 上下文与缓存命中

> 2026-11-15 写。为 101 号 weareone 的实验补概念说明。
> 所有数字来自本机真实会话日志，能自己重算。凡是我推断而不是量出来的，都标了。
> 读完你能自己算一笔账：这个任务大概花多少钱，钱花在哪。

---

## 一、一句话

**上下文就是你每次跟模型说话时，连同这句话一起寄过去的全部东西。缓存命中就是这堆东西里、厂商上次已经算过的那部分，收你便宜价。**

模型没有记忆。它不记得上一步说过什么，除非你把上一步再给它一遍。

---

## 二、上下文是什么，为什么每步都要重发

一次调用的样子：

```
[ 系统提示 37K ] + [ 你说过的话 ] + [ 模型写过的话 ] + [ 工具调用与结果 ] + [ 这次的新输入 ]
       全部寄过去 → 模型读一遍 → 吐一段输出
```

第二步调用的样子：

```
[ 系统提示 37K ] + [ 全部历史（比上一步长了） ] + [ 这次的新输入 ]
```

**所以第 100 步的输入，是前 99 步的全部内容加上这次的。** 每一步都在重发。

这不是模型懒，是没有别的地方放。它一次调用只能看见这一次寄过去的东西，没有任何跨调用的内存。

### 实测一条曲线

拿实验 1 的 A 组（单会话，106 次调用）逐条读日志：

| 第几步 | 新内容 | 缓存命中 | **这一步的上下文总量** |
|---:|---:|---:|---:|
| 1 | 19,152 | 23,296 | 42,448 |
| 2 | 1,903 | 42,368 | 44,271 |
| 3 | 10,012 | 44,160 | 54,172 |
| 10 | 194 | 55,296 | 55,490 |
| 30 | 137 | 64,896 | 65,033 |
| 50 | 218 | 74,112 | 74,330 |
| 80 | 130 | 88,192 | 88,322 |
| 106 | 2,612 | 98,560 | **101,172** |

（单位都是 token。「新内容」是新输入，「缓存命中」是重发但被缓存的那部分，两者相加才是一步的实际上下文。）

看两件事：

1. **上下文从 42,448 涨到 101,172，涨了 2.4 倍。** 任务没变大，涨的全是历史。
2. **新内容那一列很小，几十到几千。** 大部分是重发。第 30 步只新写了 137 个 token，但要寄 65,033 个。

把 106 步的上下文全部加起来：**8,008,755 token**。这就是计费量。产出的代码是 403 行。

---

## 三、重复自我介绍占多少：token 一半，钱不到两成

上面第 1 步的 42,448 里，有一块是**跟任务无关的固定开销**：人格文件、工作区指令、技能目录、工具定义。这部分每次都一样。

按本机实测的比例估（110K 字符，中文约 3 字符 1 token），这块大约 **37,000 token**。

**按 token 量算：**

```
37,000 × 106 步 = 3,922,000
3,922,000 / 8,008,755 = 49%
```

**按钱算只有 18%**，因为这一大段是稳定的前缀，几乎每次都能命中缓存：

```
3,922,000 × ¥0.0119/百万 = ¥0.0467
¥0.0467 / ¥0.2561 = 18%
```

**同一堆 token，占量一半，占钱不到两成。** 这就是缓存的作用。

反过来看更清楚：如果这 3.92M 一分钱折扣都没有，按新输入价算要 ¥2.35，是 A 组实际账单（¥0.2561）的 9 倍。

所以 `DESIGN.md` 11.1 节那三条「干净」要求（瘦人格、瘦工作区指令、不装无关技能）值不值钱？**值，但别指望砍一半就省一半。** 砍掉一半固定注入，省的是总量的 9% 左右，因为缓存已经先帮你打了五十一折。

**真正贵的是输出和历史累积，不是固定注入。**

## 四、缓存命中：厂商帮你记住了前缀

既然每次都要重发几百 K，为什么账单没那么吓人？

因为**前面那一大段通常跟上一次一模一样**。厂商会把这部分的中间计算结果存起来，下次遇到相同的前缀就直接复用，只收很少的钱。

三个条件要一起满足（**通用机制，本机没逐条验证**）：

1. 前缀完全一致。**改一个字符就不算命中**，哪怕只是补了个空格。
2. 通常只对整块（比如 128 token 一块）生效，长度不足一块的尾巴不命中。
3. 有存活时间，隔太久会失效。

这解释了几件真实的事：

- **同一个会话里连续调用，命中率极高。** 实测 A 组 106 步里，缓存命中占「新输入 + 缓存」总量的 **98.9%**（7,923,968 / 8,008,755）。
- **新开会话第一次也能命中一部分。** A 组第 1 步就有 23,296 命中，因为人格文件和工具定义跟之前某个会话相同。
- **改人格文件会让下一次调用变贵**，因为整条前缀作废，第一次要全额重算。这条是机制推断，没在本机对照测过。

### 窗口和缓存不是一回事

两个词天天一起出现，管的是两件不同的事，别混。

| | 上下文窗口 | 缓存命中 |
|---|---|---|
| 管什么 | 一次最多能装多少 | 装过的要不要重新掏钱 |
| 超了会怎样 | 装不下。要么压缩历史，要么丢掉旧消息，要么直接报错 | 不会超。没命中就按原价付 |
| 单位 | token（本机这个模型是 1,000,000） | 比例（命中占多少） |
| 谁在乎 | 长任务的可行性 | 账单 |

一条经验：**窗口大不等于免费。** 1M 窗口装满了，一次调用就是 100 万 token，哪怕全命中缓存也是 100 万 × 的一份钱。

本机那条「种子长度必须低于窗口 60%」的闸门（`SCHEMA.md` 第 4 节），防的是装不下，不是防贵。两件事要各设一条闸。

## 五、三个计费项，单价差五十倍

2026-11-15 从 [ModelGo 的 deepseek-v4.1-flash 模型页](https://modelgo.ai/zh/models/deepseek-v4.1-flash)读到，6 折档，USD 每百万 token：

| 项 | 单价 | 相对输入 | 什么时候产生 |
|---|---:|---:|---|
| 输入（新内容） | 0.0909 | 1 | 每次调用的新增部分 |
| **缓存命中** | **0.0018** | **1/51** | 重发但前缀被复用过的那部分 |
| **输出** | **0.3636** | **4 倍** | 模型写出来的每个 token |

峰值时段（09:00–12:00、14:00–18:00，北京时间）翻倍。

三个数记住两个比例就够：**缓存命中是输入的五十一分之一，输出是输入的四倍。**

为什么输出最贵：输入是一次并行读完的，输出要一个一个往外蹦，每蹦一个都要跑一遍模型。慢，所以贵。

## 六、一条公式，能算总账

```
总成本 = 所有步的上下文相加
```

这是准确的定义，只是不好直接用。拆开看：

```
一步的上下文 ≈ 基础量 + 已经堆了多少历史
              = B + g × 已经走到第几步

n 步加起来:
总上下文 ≈ n × B + g × n² / 2
```

- `B` 是基础量：系统提示 + 工具定义 + 任务原文，每步都要付
- `g` 是每步新增多少历史：这一步写了多少字、调了多少工具

用 A 组验一遍：n = 106，B ≈ 50,000，g ≈ 476（从第 10 步到第 106 步，上下文涨了 45,682，除以 96 步）

```
106 × 50,000        = 5,300,000
476 × 106² / 2      = 2,674,000
                     ─────────
合计                  7,974,000    实测 8,008,755，差 0.4%
```

**这条公式告诉你两件事：**

1. `n × B` 是线性的。步数翻倍，这一项翻倍。
2. `g × n² / 2` 是平方的。步数翻倍，这一项变四倍。

步数少的时候前一项占大头，步数多了后一项吃掉一切。106 步时是 5.3 对 2.7；306 步时是 15.3 对 18.9。

（306 步那一行用的 `g` 是 414，比 A 的 476 小。原因是四段每段都重新起算历史，`g` 只在段内累积，段与段之间清零。代进 306 × 50,000 + 414 × 306² / 2 = 34,682,652，实测 34,701,148，差 0.05%。）

## 七、用它解释一件事：「拆段压上下文」为什么是错的

我一开始也这么以为：把一条长任务切成几段，每段上下文短了，应该省钱。实测不是。

四段 B 组和单会话 A 组对账：

| | A 单会话 | B 四段 |
|---|---:|---:|
| 步数 n | 106 | **306** |
| 上下文总量 | 8,008,755 | 34,701,148 |
| 平均单步上下文 L | 75,554 | **113,402** |
| n × L | 8,008,755 | 34,701,148 |

步数涨 2.887 倍，平均单步上下文涨 1.501 倍，乘积 4.334，跟实测的 34,701,148 / 8,008,755 = 4.333 对得上。

**两个因子都涨了，一个都没降。**

为什么单步还变长了：因为每一段都要背着前面所有段交出的文档。审查段背着设计 24.5K + 改动 12K，修补段再背审查 16K + 修复 21K。文档是有利息的。

然后单价这一层还有第二次翻转。拿两段对单会话算账（`demo\prices.json` 的实价）：

| 项 | 变化 | 单价（¥/百万） | 金额变化 |
|---|---:|---:|---:|
| 缓存命中 | −2,228,224 | 0.0119 | **−¥0.0265** |
| 输入 | +55,775 | 0.59994 | **+¥0.0335** |
| 输出 | +30,323 | 2.39976 | **+¥0.0728** |
| 净变化 | | | **+¥0.0798** |

**省的是最便宜的那一项，多花的是最贵的那一项。** 所以总 token 少了 27%，钱却多了 31%。

## 八、我踩过的三个坑

**坑一：用字符数当 token。**

我在第一份实验报告里就这么干的，还写了「日志里没有用量字段」。实际有，只是字段名是 `inputTokens` 而我按 `input_tokens` 搜的。

字符和 token 的比例随内容变：中文约 1.5 字符 1 token，英文约 4 字符，代码和 JSON 更接近 3 到 4。用字符乘一个固定系数，误差能到一倍半。**有真实用量就别算代理指标。**

**坑二：以为「上下文变短」等于「便宜」。**

要问清是哪个短了：单步的短了，还是总步数少了。**真正管用的是步数。** 拆段如果让步数涨了 2.9 倍，单步再短也救不回来。

**坑三：以为缓存便宜，多读点没关系。**

缓存命中是便宜，五十一分之一。但拆段同时在多写：多写一个决定清单、多写一份改动说明，而输出是输入的四倍价。**省一项便宜的去多付一项贵的，账可能倒着走。**

## 九、你自己怎么算

三步，都能重放。

**第一步，拿到三个数。** 会话日志在 `~\.dsh\sessions\<项目>\<会话id>\session.v4.jsonl.zstd`，是多帧 zstd。按 magic `28 B5 2F FD` 切开逐帧解，每条 `assistant/message` 的 `usage` 里有 `inputTokens` / `cacheReadTokens` / `outputTokens`。

**第二步，累加。**

```
新输入 = Σ inputTokens
缓存命中 = Σ cacheReadTokens
输出 = Σ outputTokens
上下文总量 = 新输入 + 缓存命中     ← 这是计费量
```

**第三步，乘单价。** 单价在 `101-weareone\demo\prices.json`，按会话时间判断峰值还是非峰值。

现成工具：`node 101-weareone\demo\tools\collect.mjs --all` 会把五个会话全算一遍，`measure.mjs --id <会话id>` 算单个会话。

### 拿来判断一件事够不够便宜的三个数

| 数 | 怎么算 | 用途 |
|---|---|---|
| 总花费 | 三步算出来的 | 这次任务花了多少 |
| **每步平均上下文** | 上下文总量 / 步数 | 上下文工程做得好不好，越小越好 |
| **每交付一行成本** | 总花费 / 产出代码行数 | 跨任务比，不受规模影响 |

第三个数最有用。实验 1 实测：单会话 ¥0.000635 每行，两段 ¥0.000249，四段 ¥0.000662。同样的活，中间那个便宜 2.5 倍，因为它多交出的东西（决定清单）本身就是产出。

## 十、边界：这些我没验证

- **单价只对了一家。** ModelGo 的 deepseek-v4.1-flash，2026-11-15 的 6 折档。换模型换站要重查，别套用。
- **没有拿真实账单对过账。** 我是拿「页面标价 × 日志 token」算的，没跟充值记录核。误差可能在 10% 以内，也可能不。
- **缓存机制的三条是通用描述，不是本机实测。** 前缀必须完全一致、按块命中、有存活时间，这三条我没做对照实验。
- **37,000 token 的固定开销是估算。** 来自 110K 字符 ÷ 3，真实值要从请求体里数，没数过。
- **单条曲线的 `g` 会随任务变。** 写 HTML 的会话和查资料的会话，每步新增的历史量不一样。B=50K、g=476 只对这一个会话成立。
