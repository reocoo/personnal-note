# AI 记忆系统：本机怎么实现的，什么做法有效，哪里会静默失效

> 全部结论来自 2026-11-07 对本机 DSH 的实测，不是转述。数字可复算，方法在 §六。
> 判断依据来自 `81-AI沙龙会议纪要\02-会议纪要-归纳.md`：memory 管偏好，事实走检索，description 决定触发，索引常驻正文按需。

---

## 一、先拆一个误解：这个本机上没有「一个记忆系统」

说「AI 的记忆」时容易想成一个数据库。本机实际有**四条互不相干的通道**，各自被不同的代码读、在不同的时机进上下文、失效方式也不同。把它们当一件事处理，改一条会踩到另一条。

| 通道 | 承载什么 | 谁读它 | 什么时候进上下文 | 实测体量 |
|---|---|---|---|---|
| **人格/纪律** | 我是谁、怎么做事 | 第三方插件 `dsh-purge` | 每轮固定 | 29,925 B |
| **项目约定** | 这个工作区怎么干活 | DSH 内置 `dsh-agent-instructions` | 每轮固定，有预算上限 | 93,338 B（实际只进 65,536） |
| **技能索引** | 有哪些能力、什么时候用 | DSH 内置技能装配 | 每轮固定，只有 name+description | 42,052 B / 129 条 |
| **历史事实** | 做过什么、上次怎么修的 | `obelisk` CLI，**默认不读** | 只在我主动查时才进 | 538 会话 / 228.1 MB |

**关键差别在最后一列之外的那一栏**：前三条是「不做任何事也会花掉」，第四条是「不做任何事就不存在」。这决定了改造成本的方向完全不同。

## 二、四条通道各自的开关在哪（源码级）

### 2.1 项目约定通道：只认 4 个文件名

`dsh-agent-instructions\lib\index.js:17`：

```js
const DEFAULT_INSTRUCTION_FILE_CANDIDATES = ["AGENTS.md", "CLAUDE.md"];
const DEFAULT_LOCAL_INSTRUCTION_FILE_CANDIDATES = ["AGENTS.local.md", "CLAUDE.local.md"];
```

**这意味着一条硬规则**：想让它每轮读到，文件必须叫这四个名字之一。叫 `REGISTRY.md`、`NOTES.md` 的内容，放得再重要也不会被自动读。

这是「渐进式披露」在本机的实现方式：把内容从这四个名下搬走，等于让它退出常驻。搬回来才能恢复。

### 2.2 人格通道：靠插件，不靠 DSH 核心

DSH 核心的 `dsh-system-prompt` 只有两个字符串字段，不读 md 文件。真正读 `~\.dsh\prompt-inject.md` 的是第三方插件 `dsh-purge`，它**只读这一个路径**，没有目录扫描、没有 import。

**推论**：拆人格文件不能拆成两个物理文件。第二份文件不会进上下文，而且**不报错**。要分层只能在同一个文件里显式分节。

### 2.3 检索通道：工具已装，流程未接

`obelisk` CLI 0.3.0 已在本机，索引里 522 条 DeepSeek Harness 会话。它**认得**本机的 `.zstd` 格式。

它按需调用，不调用就等于不存在。这正是 `81 号纪要` 说的「事实走检索」：

> 只有稳定不变、一直需要注入的东西，才值得做成 memory 或写进 `AGENTS.md`；其余按需查。

### 2.4 技能索引通道：description 是唯一的触发闸门

129 条 description 合计 38,493 B，均值 298 B/条。正文（`SKILL.md`）不常驻，只有索引常驻。

**实测发现一处之前没人写的机制**：索引会按 **500 字符**截断 description。`sw-dialogue` 原文 1,026 B / 954 字符，进索引后只剩 500 字符。所以「写长 description 让它更准确」这个想法在索引层是无效的，超出的部分永远不会被模型看到。

## 三、预算与截断：最贵的一处静默失效

### 3.1 机制

`agent-instructions` 有 65,536 字节预算。超了怎么处理，日志头一行写得很清楚：

```
Workspace instruction budget 65536 bytes: omitted ~/.dsh/AGENTS.md; truncated AGENTS.md from 91789 to 65117 bytes
```

两种处理方式：**整体省略**（`omitted`）和**尾部截断**（`truncated`）。两者都不报错、不警告，界面上零提示。

### 3.2 实测后果

当前 `AGENTS.md` 93,338 B，进上下文 65,117 B，**丢 28,221 B**。丢的是文件尾部的段落，按顺序包括「领号规则」「关键环境约束」「写代码约定」「已知未解决」「自检清单」。

**所以这个机制的恶劣之处**：它砍的正好是文件末尾。而文件末尾通常是最近加的东西，也是还没读过的。**你以为写进去了，其实下一次会话读不到。**

### 3.3 一处容易误判的地方

`~\.dsh\AGENTS.md`（3,746 B）被 `omitted` 是另一件事。它的内容是一份破甲红队探针（`# probe-bottomline-v1`），**不是**用户约定。它被省略不构成损失。

**方法论启示**：看到 `omitted` 不要直接判成「重要内容丢了」。先打开那个文件看是什么。

## 四、可实行的措施（每条带判据与实测数）

### 措施 1 · 用「结构性」而不是「总量」控制常驻

单看总量没用。实测 `AGENTS.md` 的段落分布是极不均匀的：

| 段 | 字节 | 占比 |
|---|---|---|
| 编号登记表 | **72,197** | **77.4%** |
| 其余 10 段合计 | 21,141 | 22.6% |

一段占了四分之三。这种情况下「精简文字」的收益几乎为零，**动结构才有效**：把这段搬出 `AGENTS.md`（改叫 `REGISTRY.md`），常驻立刻从 93,338 降到约 21,400。

**判据**：先量段落分布，找出占比超过 50% 的那一段。找不到这样的段，才轮到改文字。

### 措施 2 · 判断「该常驻还是该按需」用可操作的判据

`81 号纪要` 那条「稳定不变、一直需要注入」太抽象，套到具体文件上判不出来。可操作的版本是三个连问：

1. **这段内容变了，我的行为要不要跟着变？** 不要变 → 不该常驻
2. **要变的话，是这一轮就要变，还是下次碰到相关任务才变？** 后者 → 按需
3. **不读它，我这一轮会不会做错事？** 不会 → 按需

拿本机的登记表套一遍：它变了，我的行为确实要变（要按新编号建目录）。但**不是这一轮就变**（只有建目录那一刻才需要）。不读它，写代码、答疑、画图都不受影响。**推出来的结论是按需。**

**判据本身要能反过来用**：拿一段没见过的内容，这三个问题能给出答案，不需要再讨论。给不出，说明判据还是太抽象。

### 措施 3 · 把 description 当接口签名写，不当简介写

索引按 500 字符截断，且每条约 300 B 的平均成本意味着**每加一条 skill 就固定多花 300 B**。

有效做法：
- 写「什么时候读 + 用户会说什么词」，不写「这是什么」（触发靠前者）
- 控制在 250 字符以内，留出余量，别写到截断线上
- 同类合并。实测 `caveman` 族 13 条、`ponytail` 族 6 条，description 互相高度重叠，合并主干能省一大截

**判据**：一条 description 读完，能不能说出「什么请求会让它被选中」。说不出就是简介，不是接口。

### 措施 4 · 用一个开关主动关闭不需要的 skill

本机已有这个机制，只是容易忘：

```yaml
disable-model-invocation: true
```

带这个标记的 skill **不进索引**（省 description 那份常驻），但仍能手动 `/skill-name` 调用。实测 142 个目录里有 4 个这样：`grill-me` / `i-have-adhd` / `prompt-generator` / `quick-mode`。

**方法论价值**：省常驻不一定靠删。**「关掉自动触发但保留手动调用」是零损失的一档**，优先于删除或合并。

### 措施 5 · 把历史事实交给检索，别压成结论

`81 号纪要` 讲的失败链条值得记住：

```
弱模型把一条规则写进 memory
  → 后续 agent 读到，认为这就是事实
  → 失去继续探查的动机
  → 照错的方案做
  → 全程不报错，人以为它做对了
```

本机对应的正确做法是走 `obelisk`：查得到原始会话、带 session id 与时间戳，能追到出处。压成一句「XX 已经解决了」就失去了追溯能力。

**判据**：这条记录**能不能回溯到原始证据**。能 → 可以进记忆；不能 → 它只是个说法。

### 措施 6 · 分层要按「过期方式」分，不按主题分

本机 `prompt-inject.md` 29,925 B 的实际分布：

| 层 | 字节 | 占比 | 过期方式 |
|---|---|---|---|
| 不变式层（纪律、判据） | 24,931 | 83.3% | 几乎不变 |
| 领域层（硬件、路径、坑位） | 3,929 | 13.1% | 随版本变化 |

**按主题分是分不开的**（「写代码」既是纪律又是环境约束）。按过期方式分才有唯一解：领域层应该下沉成 skill，索引只留一句指路。

同时这也纠正了改造计划里的一个算错的数：原来写「领域事实约占四成」，实测是 13.1%。**把领域层全砍光也只能从 29,925 降到 25,996，到不了 20 KB。**

## 五、这些地方会静默失效（最贵的清单）

四条通道的失效方式各不相同，共同点是**都不报错**。

| 失效 | 症状 | 判据 / 检测方法 |
|---|---|---|
| 项目约定超预算截断 | 界面正常，行为缺一块 | 看会话日志 `agent-instructions` 段有没有 `truncated` / `omitted` |
| 内容搬到非四文件名 | 写了但永远读不到 | 检查文件名在不在 `["AGENTS.md","CLAUDE.md","AGENTS.local.md","CLAUDE.local.md"]` |
| 第二份人格文件 | 写了完全不生效 | 只有 `$DSH_HOME/prompt-inject.md` 一个路径被读 |
| description 超 500 字符 | 后半段永远不被看见 | 量字符数 |
| skill 漏进索引 | 有 `SKILL.md` 但调不到 | 对比目录数与索引条目数；先查 `disable-model-invocation` |
| 检索覆盖不全 | 查询结果缺一部分历史 | obelisk 索引 538 vs 磁盘 582，缺 44（7.6%，成因未查） |
| memories 表空 | 以为在做记忆，实际一条没有 | `SELECT COUNT(*) FROM memories` = 0 |

**最后一条值得单独说**：本机 `~\.obelisk` 数据目录存在、CLI 能用、索引有 538 个会话，看起来"记忆系统在工作"。但 `memories` 表是 **0 行**。**「工具装好了」和「记忆在积累」是两件不同的事**，前者是后者既不充分也不必要的条件。

## 六、怎么自己量（方法，不是结论）

所有数字都可以复算。核心三步：

**第一步，拿会话日志。** `~\.dsh\sessions\<项目目录>\<session-id>\session.v4.jsonl.zstd`。多帧拼接，必须用 `zstandard.stream_reader`，用 `decompress` 只解第一帧，会看起来像「日志很小」。

**第二步，按事件类型分账。** 事件顺序：
```
turn/start → step/start → system/message → user/message(注入×4)
→ request/header → assistant/message → tool/call → tool/result
```

固定注入在 `system/message` 和 4 条 `user/message` 上，按 `data.content[0].text` 取正文。

**第三步，量的时候要拿对字段。** 这一步我踩过坑，写下来免得别人再踩：

- 取正文用 `content[0].text`。**不要递归抓所有 `text` 键**，`source.sections[]` 里有同名字段，会重复计数。我因此把 830 量成 1,570，把一个正确的数字判成错的。
- 工具定义在 `data.header.tools`，不是 `data.tools`。取错会得到「这次请求没有工具定义」的假结论。

**通用规矩**：拿自己脚本的输出当证据之前，先验脚本本身。**只抽「值」不抽「提取器」，是最容易漏的一层。**

## 七、这一层的通用判据汇总

| 要判断 | 判据 |
|---|---|
| 这段该常驻吗 | 变了要改行为？这一轮就要改？不读会做错？三问有一否即按需 |
| 这条记录能进记忆吗 | 能不能回溯到原始证据 |
| 改哪个文件才有效 | 文件名在不在那 4 个里 |
| 这层该不该下沉 | 它的过期方式和上层一样吗 |
| 精简先动哪里 | 段落分布里占比超 50% 的那一段 |
| 这个「没问题」可信吗 | 是主动探测过，还是只是没看见问题 |
| 数对了没 | 先验提取器，再验值 |

## 九、证据边界

**实测（可复算）**：171,867 B 的五段拆解、65,536 预算、截断点 65,117、93,338 与 28,221 损失、登记表 72,197 / 92 行、`prompt-inject.md` 29,925 与 83.3% / 13.1%、索引 129 条与 500 字符截断、142 目录 / 133 唯一名 / 4 个 `disable-model-invocation`、obelisk 538 vs 磁盘 582、`memories` 表 0 行、`request/header` 176,481 B / 160 工具 / MCP 占 54.8%。

**未探测**：44 个未索引会话的成因；`REGISTRY.md` 不注入后领号会不会漏；token 真实用量（日志有 `input_tokens` 字段但没取）。

**改判过的地方**（写在明处）：曾用递归抓 `text` 键的方式量出 runtime 830 / time 262 是"字符"，据此判定量纲混用。实测 `content[0].text` 的 bytes 就是 830 / 262，**原判断错误，已撤回**。
