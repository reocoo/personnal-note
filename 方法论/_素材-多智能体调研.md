# 素材：主流多智能体项目的任务拆分、协调、人机对接

> 这是一份**原料**，不是文章。写文章的人可以从中挑事实、挑原话、挑数字。
> 采集时间：2026-11-14。所有结论后面带出处 URL，方便回去核。
> 只讲三件事：**怎么拆任务 / 怎么协调 / 人从哪儿进来**。另加一问：**它自己承认哪些地方不行**。
> 不涉及模型训练、推理优化、评测基准设计。

## 0. 口径说明（读这份材料前先看）

| 标记 | 含义 |
|---|---|
| 「原文」 | 我直接读到了论文 HTML 或官方文档页面正文 |
| 「二手」 | 只看到别人的转述，没读到原文。本文件里只有一处，见 §7 |
| 「推断」 | 我根据读到的原文自己下的判断，不是原文写的话。会标出来 |

术语先解释一次，后面直接用：

- **SOP**（Standardized Operating Procedure，标准作业流程）：把一个复杂任务固定成「谁先做、交什么、交给谁」的流程表。MetaGPT 的核心就是这个。
- **PRD**（Product Requirements Document，产品需求文档）：产品经理写的那份「要做什么功能、给谁用」的文档。
- **黑板**（blackboard）：多个执行者共享的一块公共存储区，谁都能往上写、谁都能读。MetaGPT 的 message pool 就是这个东西的工程版。
- **checkpoint**：把某一刻的运行状态整个存下来，之后可以从这里重新开始。
- **SSE**（Server-Sent Events，服务器推送事件）：一种 HTTP 上单向持续推送的技术，用来边跑边把进度吐给前端。
- **token**：模型计费和计长的单位词，约等于「字的一部分」。报价单里说「用了多少 token」，就是这个东西。

## 1. MetaGPT

定位：把人类软件公司的 SOP 编码进 prompt 序列，用「流水线」的方式让不同角色接力产出一份软件。

出处：arXiv:2308.00352v7（2024-11-01 修订版）<https://arxiv.org/abs/2308.00352>，正文 HTML <https://arxiv.org/html/2308.00352v7>

### 1.1 怎么拆任务

- **按角色拆，而且角色是固定 5 个**：Product Manager（产品经理）、Architect（架构师）、Project Manager（项目经理）、Engineer（工程师）、QA Engineer（测试工程师）。原文：「We define five roles in our software company」。（来源：v7 §3.1 Specialization of Roles）
- **每个角色不只名字，还有四样设定**：profile（名字+身份）、goal（目标）、constraints（约束）、以及自己的工具与上下文。比如产品经理能用网页搜索，工程师能执行代码。（同上）
- **真正的切分依据不是角色，是「中间产物」**：产品经理交出 PRD（含 User Stories 和 Requirement Pool），架构师交出 File Lists / Data Structures / Interface Definitions（文件清单、数据结构、接口定义），项目经理据此派活，工程师照着写类与函数，QA 出测试用例。（同上，§3.1 Workflow across Agents）
- 也就是说：**上一环的交付物格式，就是下一环的输入契约**。角色只是这些交付物的生产者标签。

### 1.2 怎么协调

- **没有中心调度器**。原文用的是 publish-subscribe（发布-订阅）：所有 agent 往一个共享 message pool（消息池）里发布自己的结构化消息，也从中读别人发的。（来源：§3.2 Publish-Subscribe Mechanism）
- **靠订阅过滤，避免信息过载**：每个 agent 按自己的角色兴趣只订阅相关消息，例如架构师主要盯 PRD，不太关心 QA 的文档。「an agent activates its action only after receiving all its prerequisite dependencies」（收到全部前置依赖才动）。（同上）
- **不用对话，用文档**：原文明确对比 ChatDev，「agents in MetaGPT communicate through documents and diagrams (structured outputs) rather than dialogue」。（来源：§3.2 Structured Communication Interfaces）
- **冲突怎么裁**：论文里没有「仲裁」机制。冲突靠流程顺序消解，谁在前谁的定义优先；代码层面的冲突靠**可执行反馈**兜底：工程师自己写并跑单测，失败了就调试，最多重试 3 次（「until the test is passed or a maximum of 3 retries is reached」）。（来源：§3.3 Iterative programming with executable feedback）
- 一句可以直接引的：论文说纯自然语言闲聊会让 agent 之间浪费大量轮次，举的例子是「Hi, hello and how are you?」这类寒暄。这是它改用结构化文档的理由。（来源：§1 Introduction）

### 1.3 怎么跟人对接

- 人只在**两个位置**出现：开头给一句需求，结尾看产物。论文没有设计中途审批环节。
- 官方对「人的控制权」的说法是：「Humans can initiate, observe, and stop running with the highest level of control」，即人可发起、可观察、可停止。（来源：Appendix D.2 Transparency and Accountability）
- 但同一份论文的局限章节自己承认：**「A key challenge for users is to interrupt the running process of each agent, or set the starting running point (checkpoint) for each agent.」** 也就是「中途打断某个 agent、或给它设一个起点」对用户来说是难题。（来源：Appendix D.1 Limitation, Human user side）

### 1.4 承认的失败场景

- **前端/UI 类场景做不了**：还没接入做界面的 agent 和多模态工具。（Appendix D.1, System side）
- **产量大但撑不住真实应用**：「despite generating the most amount of code among comparable frameworks, it remains challenging to fulfill real-world applications' diverse and complex requirements」。（同上）
- **自我审查会漏错**：第一版实现时，代码 review 环节因模型幻觉漏掉了某些错误，所以才改写成「真跑一遍」的可执行反馈。（来源：§3.3 开头）
- **早期就踩过幻觉链**：论文摘要里点名「cascading hallucinations caused by naively chaining LLMs」是把简单串联模型搞崩的原因。（来源：Abstract）
- 附一组它能拿出来对比的数（**都是论文自己的实验，SoftwareDev 数据集上随机取 7 个任务**）：

| 指标 | ChatDev | MetaGPT（无反馈） | MetaGPT |
|---|---|---|---|
| 可执行性（1~4 分，人工评） | 2.25 | 3.67 | 3.75 |
| 运行时间（秒） | 762 | 503 | 541 |
| token 用量 | 19,292 | 24,613 | 31,255 |
| 生成文件数 | 1.9 | 4.6 | 5.1 |
| 总代码行数 | 77.5 | 194.6 | 251.4 |
| 每行代码耗 token | 248.9 | 126.5 | 124.3 |
| 人工修订次数 | 2.5 | 2.25 | 0.83 |

（来源：v7 Table 1）

- **加角色到底有没有用，论文给了一张消融表**，这个数最值得引：1 个 agent（只有工程师）出 83 行代码、人工修订 10 次、可执行性 1.0；加到 4 个 agent（工程师+产品+架构+项目经理）出 191 行、修订 2.5 次、可执行性 4.0。**角色从 1 加到 4，人工修订降到四分之一，代码量翻一倍多，成本从 $0.915 涨到 $1.385**。（来源：v7 Table 3）

## 2. ChatDev

定位：虚拟软件公司。跟 MetaGPT 最大的区别是「靠多轮对话推进」，不是靠文档。

出处：arXiv:2307.07924v5（ACL 2024，2024-06-05）<https://arxiv.org/abs/2307.07924>，正文 HTML <https://arxiv.org/html/2307.07924v5>

### 2.1 怎么拆任务

- **三层结构，硬编码在代码里**：Chat Chain（聊天链）→ Phase（阶段）→ Subtask（子任务）。三个阶段固定是 design（设计）、coding（编码）、testing（测试）；编码再拆成写代码与补全代码，测试再拆成代码审查（静态测试）与系统测试（动态测试）。（来源：§3.1 Chat Chain）
- **一共 5 个子任务，配 5 个角色**：「We divided software development into 5 subtasks within 3 phases, assigning specific roles like CEO, CTO, programmer, reviewer, and tester.」（来源：§4 Implementation Details）
- **每个子任务只有两个 agent**：一个 instructor（指导者，下指令）一个 assistant（执行者，给方案），多轮对话到达成共识为止。论文明说这是为了「avoiding complex multi-agent topologies」（避开复杂的多智能体拓扑）。（来源：§3.1）
- **子任务什么时候结束有明确数字**：「after two unchanged code modifications or after 10 rounds of communication」，即代码连续两次改不动、或者聊满 10 轮，就收。（来源：§4 Implementation Details）

### 2.2 怎么协调

- **靠链式顺序**，不是靠调度器。上一环产出的 solution 作为下一环的输入。
- **记忆被切成两层**：short-term memory 记本阶段内的对话，long-term memory 只带「上一阶段得出的结论」过去，不搬整段对话历史。原文的理由是避免被过量信息淹没。（来源：§3.1 Memory）
- **冲突靠一种叫 communicative dehallucination（沟通式去幻觉）的机制**：让 assistant 在正式作答前**反客为主**，先向 instructor 追问更具体的细节（比如依赖包的确切名字和类），拿到明确答复再动手。原文把这个叫「role reversal」（角色反转）。（来源：§3.2 Communicative Dehallucination）
- 一句可以直接引的实验观察：**自然语言适合谈系统设计，编程语言适合调试**（「their utilization of natural language is advantageous for system design, and communicating in programming language proves helpful in debugging」）。（来源：Abstract）

### 2.3 怎么跟人对接

- **人只在开头**：给一句需求描述（例如「develop a Gomoku game」）。之后全程自动，论文用「prompt engineering that only takes place at the start of each subtask round」描述这个设计。（来源：§3.1 Agentization）
- **人出现在评估环节，不在运行环节**：论文用人工和 GPT-4 双评委做 pairwise 比较（成对比较，避免顺序偏差）。（来源：§4.1 Overall Performance 与 Table 2）
- 数据集也是「LLM 生成 + 人工后处理」：SRDD 共 1,200 条需求描述，分 5 大类 40 子类、每子类 30 条。（来源：§4 Datasets）

### 2.4 承认的失败场景（这一节原文写得很实）

来源：§6 Limitations

- **能力可能被高估**：agent 常只实现简单逻辑，**信息密度低**。
- **需求不清晰就崩**：没有清楚详细的需求，agent 抓不住任务意图。原文举了两个例子：说「做个贪吃蛇」就只给个最朴素的版本；做信息管理系统时，agent 可能去读静态的键值占位符，而不是真的连数据库。
- **只适合原型，不适合真实复杂应用**：「these technologies are more suitable for prototype systems rather than complex real-world applications」。
- **通用软件没法自动评**：函数级代码可以用 pass@k，整个软件不行。人工评大规模数据集不现实。
- **多智能体更贵更慢**：比单 agent 消耗更多 token 和时间，增加算力需求与环境负担。论文还提了一句希望「用更少的交互达到同样能力」。
- 附它的成绩（自己的论文自己的数据集）：Completeness 0.5600、Executability 0.8800、Consistency 0.8021、Quality 0.3953；平均耗时 148.21 秒、22,949 token、4.39 个文件、144.3 行。（来源：Table 1 与 Table 3）

## 3. AutoGen / AG2

这两个要分开说清楚，因为它们是**两条线**：

| | AutoGen | AG2 |
|---|---|---|
| 谁维护 | 微软 | 社区（ag2ai），是 AutoGen 0.2 那条线的延续 |
| 抽象 | AgentChat（高层 Teams）+ Core（事件驱动运行时） | ConversableAgent + GroupChat + GroupChatManager |
| 官方文档 | <https://microsoft.github.io/autogen/stable/> | <https://docs.ag2.ai/latest/> |

（AG2 与 AutoGen 的谱系关系：AG2 文档站自述其代码库为 `ag2ai/ag2`，<https://docs.ag2.ai/>；微软侧的 Teams/Selector 等属于新版 AgentChat。两边 API 不通用这一点是**推断**，依据是文档里同一概念用了不同类名。）

### 3.1 怎么拆任务

AutoGen 路线（AgentChat）：

- **不预设拆分方式，给的是「团队预设」让你自己选**。官方列的预设：RoundRobinGroupChat（轮流说）、SelectorGroupChat（由模型选下一个说的人）、Swarm（靠 handoff 消息交接）、MagenticOneGroupChat（通用型，带编排器）。（来源：<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html>）
- **Magentic-One 是唯一自带「拆解+重规划」的**：一个 Orchestrator（编排器）先做计划，把事实与猜测写进 **Task Ledger**（任务账本）；每一步再写 **Progress Ledger**（进度账本）自检；发现连续几步推不动，就改 Task Ledger 重新出计划。原文叫「outer loop 更新 Task Ledger，inner loop 更新 Progress Ledger」。（来源：<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/magentic-one.html>）
- Magentic-One 的分工是**按能力/工具拆**而不是按职业拆：WebSurfer 操作浏览器、FileSurfer 读本地文件、Coder 写代码、ComputerTerminal 跑命令。（同上）
- **官方劝退**：Teams 页开头就写「Teams are for complex tasks... they also demand more scaffolding to steer compared to single agents... start with a single agent for simpler tasks」，即先用单 agent，撑不住了再上团队。（来源：teams.html）

AG2 路线：

- **拆法靠人写死**：你自己建 GroupChat，把 agent 列表塞进去，设 `max_round`，靠 `description` 让 manager 知道每个人会干什么。（来源：<https://docs.ag2.ai/latest/docs/user-guide/advanced-concepts/groupchat/groupchat/>）
- `ConversableAgent` 是基本单位，能配 LLM、能配人（human input）、能配工具，这三者可以任意组合。论文里的定义是「AutoGen agents are customizable, conversable, and can operate in various modes that employ combinations of LLMs, human inputs, and tools」。（来源：arXiv:2308.08155 摘要 <https://arxiv.org/abs/2308.08155>）

### 3.2 怎么协调

- **有明确的调度者**：AG2 里是 `GroupChatManager`。流程是「manager 选一个 agent 说 → 该 agent 说完把消息交回 manager → manager 广播给其余所有人」，循环。（来源：AG2 GroupChat 页）
- **选人策略有四种**：`round_robin`（轮流）、`random`（随机）、`manual`（问人）、`auto`（默认，用 manager 的 LLM 选）。（同上）
- **可以给选人加硬约束**：`allowed_or_disallowed_speaker_transitions` 参数，指定「谁后面只能跟谁」，原文举例是数字 agent 后面只能接加法 agent 或自己。（同上）
- AutoGen 新版把「谁下一个说」也交给模型：SelectorGroupChat 每轮读上下文加各 agent 的 `description`，由模型选下一个发言人，然后广播。（来源：<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html>）
- **共享状态就是那段对话本身**：RoundRobinGroupChat 里「all agents share the same context」，每个 agent 发言即广播给全队，所以全队上下文一致。（来源：teams.html）
- **冲突怎么裁**：没有仲裁者，靠**终止条件**收场。可选条件包括 `TextMentionTermination`（出现某个词就停）、`MaxMessageTermination`（消息数上限）、`HandoffTermination`、`ExternalTermination`、`CancellationToken`（直接中断并抛异常）。（来源：teams.html、selector-group-chat.html）
- 值得引的一句官方原话：官方示例里用 `MaxMessageTermination(max_messages=25)` 的理由写作「to avoid infinite loop」（避免死循环）。（来源：selector-group-chat.html）

### 3.3 怎么跟人对接

- **两种接法**，官方明写：（来源：<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/human-in-the-loop.html>）
  1. **跑的过程中插话**：把 `UserProxyAgent` 放进团队，团队到某一步会调它，控制权交回给人，等人给出反馈再继续。
  2. **跑完再给反馈**：用 `max_turns` 或终止条件让团队停下，应用把状态存起来（官方指向 Managing State 页），拿到人的反馈后恢复继续。
- **谁决定什么时候问人**：RoundRobin 里按名单顺序轮到它，Selector 里由 selector 的 prompt 或函数决定。（同上）
- **官方明确警告第一种接法的代价**：`UserProxyAgent` 被调用时会阻塞整个团队，「This will hold up the team's progress and put the team in an unstable state that cannot be saved or resumed」，所以建议只用于「点个批准/否决」这类短交互。（同上）
- Magentic-One 另外提供代码执行审批：`MagenticOne(..., approval_func=...)`，执行前弹给人看代码、要 y/n。（来源：magentic-one.html）

### 3.4 承认的失败场景

- **团队不是免费的**：需要更多「脚手架」去引导，官方建议先单 agent。（teams.html）
- **插话会把状态搞坏**：`UserProxyAgent` 阻塞期间团队处于无法保存/恢复的状态。（human-in-the-loop.html）
- **群聊会死循环**：官方示例自己加消息数上限来防。（selector-group-chat.html）
- **Magentic-One 的风险清单**（官方 Caution 块，共 6 条建议 + 1 句警告）：建议放容器里跑、用虚拟环境、盯日志、保留人在环、限制网络与资源访问、别让它碰敏感数据；并明确警告「agents may occasionally attempt risky actions, such as recruiting humans for help or accepting cookie agreements without human involvement」，以及「Magentic-One may be susceptible to prompt injection attacks from webpages」（可能被网页里的提示注入攻击）。（来源：magentic-one.html）
- **大型群聊不好控**（AG2 侧原话）：「Group chat is a powerful conversation pattern, but it can be hard to control if the number of participating agents is large.」这就是它为什么要加 speaker transition 约束。（来源：AG2 GroupChat 页）
- **一个真实事故可以从官方示例里直接摘**：SelectorGroupChat 那段示例日志里，DataAnalystAgent 拿到的是错误数字（用 432 和 527 算百分比），产出了 21.99% 这个无关结果，随后 PlanningAgent 说「It seems we've missed some context there」重新派活。**选错人一次，结果就错一次，而且没人报错**。（来源：selector-group-chat.html 的 candidate_func 示例运行日志）

## 4. CrewAI

定位：把「角色 + 任务 + 团队」做成三个显式对象，让不写代码的人也能用 YAML/JSONC 描述一支 AI 团队。

出处：官方文档 v1.15.41。Crew 概念 <https://docs.crewai.com/en/concepts/crews>，Process <https://docs.crewai.com/en/concepts/processes>，Flows <https://docs.crewai.com/en/concepts/flows>，Collaboration <https://docs.crewai.com/en/concepts/collaboration>，Human Input <https://docs.crewai.com/en/learn/human-input-on-execution>，Production Architecture <https://docs.crewai.com/en/concepts/production-architecture>

### 4.1 怎么拆任务

- **三层对象，切分依据是「产出物」**：
  - Agent：`role`（角色）、`goal`（目标）、`backstory`（背景故事）、`tools`、`llm`。
  - Task：`description`（做什么）、`expected_output`（要什么形状的产出）、`context`（依赖哪些前序任务的输出）、`output_file`。
  - Crew：`tasks` + `agents` + `process`。
  （来源：crews.html 的 Crew Attributes 表与 crew.jsonc 示例）
- **任务之间的连接靠 `context` 字段显式声明**，不是靠隐式顺序。示例里分析任务的 `"context": ["research"]`，意思是我要用 research 这个任务的产出。（来源：crews.html 示例）
- **顺序执行时按数组顺序跑**：「Tasks run in the order they appear in tasks when process is "sequential"」。（同上）
- **层级模式下任务不预先分配**：原文「Tasks are not pre-assigned; the manager allocates tasks to agents based on their capabilities, reviews outputs, and assesses task completion」，由 manager 按能力派活、审产出、判完成。（来源：processes.html）

### 4.2 怎么协调

- **两种 Process**：`sequential`（默认，按顺序）与 `hierarchical`（有 manager 的指挥链）。层级模式必须给 `manager_llm` 或 `manager_agent`，否则起不来。（来源：processes.html）
- **manager 的具体职责写得很清楚**：planning（规划）、delegation（派活）、validation（校验）。（同上）
- **同级之间的横向协调靠两个自动生成的工具**：当 `allow_delegation=True` 时，agent 自动获得 `Delegate work to coworker(task, context, coworker)` 和 `Ask question to coworker(question, context, coworker)` 两个工具，即「把活甩给同事」和「问同事问题」。（来源：collaboration.html）
- **Flows 是叠在 Crew 之上的确定性编排层**：事件驱动，用 `@start()` 标入口、`@listen(x)` 监听某步完成、`@router()` 做分支，状态放在 `self.state` 里（可绑 Pydantic 模型）。（来源：flows.html）
- **冲突怎么裁**：Crew 层没有仲裁，靠 Task Guardrails（护栏函数）在接收产出前拦截，函数返回 `(False, "理由")` 就把产出打回重做；以及 `output_pydantic` / `output_json` 强制结构化，避免解析失败。（来源：production-architecture.html 的 Control Primitives 一节）

### 4.3 怎么跟人对接

- **按任务开人审**：`Task(..., human_input=True)`，开了这个 flag 的 agent 在给最终答案前会向人要输入，用途写明是「provide extra context, clarify ambiguities, or validate the agent's output」。（来源：human-input-on-execution.html）
- **粒度是「任务级」而不是「工具级」**：文档里没有看到「某个工具调用前暂停等批准」这种机制，只有任务结束前问人。（这是我从该页内容范围得出的判断，标注为**推断**）
- 另有专门的 HITL 工作流页与 Flows 里的人工反馈页（文档导航中的 Human-in-the-Loop (HITL) Workflows、Human Feedback in Flows），本次未逐页读。

### 4.4 承认的失败场景

- **官方不建议直接拿 Crew 上生产**。Production Architecture 页第一句：「When building production AI applications with CrewAI, we recommend starting with a Flow.」理由给了三条：状态管理、控制（能写循环/条件/分支）、可观测性。原话是「While it's possible to run individual Crews or Agents, wrapping them in a Flow provides the necessary structure for a robust, scalable application」。（来源：production-architecture.html）
- **Crew 要小**：「Don't over-engineer Crews: Keep them focused.」每个 Crew 只干一件事（研究一个主题、写一篇博客）。（同上）
- **参数不全会直接报错**：层级模式缺 `manager_llm` 或 `manager_agent` 就不能用，文档用 Note 单独提醒。（来源：processes.html）
- 其他局限（如成本、重复调用、幻觉）我在 CrewAI 官方文档里**没有找到集中的 Limitations 章节**，只有上面这些散落的工程建议。这一条算「未查到」的典型，见 §8。

## 5. LangGraph 的 deepagents

定位：一个「agent 外壳」（harness），把规划、虚拟文件系统、subagent、长期记忆这几件常被手写的东西做成中间件。

出处：Deep Agents overview <https://docs.langchain.com/oss/python/deepagents/overview>，Subagents <https://docs.langchain.com/oss/python/deepagents/subagents>

补一个版本线索：这套文档已从 `docs.langchain.com/labs/deep-agents/` 迁到 `docs.langchain.com/oss/python/deepagents/`，旧 URL 现在 404。（实测：<https://docs.langchain.com/labs/deep-agents/overview> 返回 404）

### 5.1 怎么拆任务

- **两套拆法并存，一套显式一套隐式**：
  1. **显式规划**：`TodoListMiddleware` 给 agent 一个 `write_todos` 工具，任务有 `pending` / `in_progress` / `completed` 三种状态，存在 agent state 里。**从 v0.7 起这是 opt-in（不默认开）**，早期版本默认带。（来源：overview，Task planning 节）
  2. **隐式拆解**：主 agent 自己判断要不要调 `task` 工具把活分包出去。
- **拆分的物理单位是「上下文窗口」**：官方给 subagent 的第一条理由是 context quarantine（上下文隔离），即把搜索、读文件、查数据库这些「输出很大」的活关在子窗口里，主 agent 只收最后那份报告。（来源：subagents 页 Why use subagents?）
- **官方给了「不要用」的清单**：简单单步任务、需要保留中间上下文、开销大于收益时，都不该开 subagent。（同上）

### 5.2 怎么协调

- **协调靠一个工具 + 一份报告**：主 agent 用 `task()` 调用，subagent「runs independently until completion」然后「returns one final report to the main agent」。（来源：overview，Subagents 节）
- **两种上下文模式**：
  - `mode: "isolated"`（默认）：子 agent 只看到你传进去的那段任务描述，看不到父对话。
  - `mode: "fork"`：继承父的完整对话历史与系统提示，好处是能复用 prompt cache，坏处是 fork 出来的子 agent **不能再调用 task**，必须自己干完。（来源：subagents 页 When to use forking 表）
- **并行怎么做**：默认路径下主 agent 可以在一个回合里发多个 `task` 调用；装了 QuickJS 解释器后还能从代码里 for 循环批量派发（叫 dynamic subagents，beta）。（来源：subagents 页 Dynamic subagents 节）
- **共享状态怎么管**：没有一个全局黑板。状态的载体是**虚拟文件系统**（overview 原话「a virtual filesystem for context」）和 agent state。官方推荐的省上下文手法就是让 subagent 把大块原始数据写进 `/data/raw_results.txt`，只回摘要。（来源：subagents 页 Troubleshooting「Context still getting bloated」）
- **冲突怎么裁**：靠父 agent 自己汇总（single handoff，只有一份报告回来），加上 `interrupt_on` 在危险工具上暂停。没有内建的仲裁者。

### 5.3 怎么跟人对接

- **按工具挂审批**：`create_deep_agent(interrupt_on={"edit_file": True})`，每次改文件前暂停，人可以「approve the call, add guidance, or modify tool inputs before execution」。（来源：overview，Human-in-the-loop 节）
- **技术底座是 LangGraph 的 interrupt**，所以暂停点、恢复、状态持久化都走 LangGraph 那一套（需要 checkpointer）。
- 粒度是**工具级**，比 CrewAI 的任务级更细；这一条是三者里最接近「每一步都能拦」的设计。

### 5.4 承认的失败场景（官方专门写了一节 Troubleshooting）

来源：subagents 页 Troubleshooting，三个都给了症状 + 解法

1. **subagent 压根没被调用**：主 agent 自己闷头干。解法是把 `description` 写具体（「Conducts in-depth research on specific topics using web search」这种），并在系统提示里明确要求委派。
2. **用了 subagent 上下文还是爆**：因为子 agent 把原始数据整段回传了。解法是要求它只回摘要（给了「500 词以内、不要原始数据」的模板），大文件落盘。
3. **叫错人**：任务给到了不合适的 subagent。解法是把两个相似 subagent 的 description 拉开差距（「1~2 次搜索的简单问题」对「需要多轮搜索与综合的复杂报告」）。

另外三条硬限制：

- **subagent 是无状态的、只能回一份报告**：「Subagents are stateless and cannot send multiple messages back.」中途没法追问。（来源：overview）
- **fork 模式下的子 agent 不能再用 task**：想再往下拆只能自己干。（来源：subagents 页）
- **dynamic subagents 还是 beta**：「APIs and lifecycle behavior may change between releases.」（来源：subagents 页）

## 6. A2A（Agent2Agent）

定位：不是框架，是**协议**。解决的是「两个不同厂商/框架的 agent 怎么互相发现、怎么派活、怎么收结果」。

出处：官方站 <https://a2a-protocol.org/latest/>。本次读了：What is A2A <https://a2a-protocol.org/latest/topics/what-is-a2a/>、Core Concepts <https://a2a-protocol.org/latest/topics/key-concepts/>、Life of a Task <https://a2a-protocol.org/latest/topics/life-of-a-task/>、规范页目录与总览 <https://a2a-protocol.org/latest/specification/>

**归属说明**：站点横幅写「A2A joins the Agentic AI Foundation」（2026-08-27 公告），页脚写「Copyright 2026 The Linux Foundation」。**「Google 发起」这一点我在官方站点正文里没有读到原文**，属于外部通识，标为未在原文核实。协议规范全文章节 3 至 13 我只读了目录与总览，没有逐节读。

### 6.1 怎么拆任务

- **协议不管你怎么拆，只管你怎么交**。它不定义内部角色、不定义规划。这个判断的依据是 Core Concepts 页列出的五个通信元素里没有任何「规划」或「角色」对象，只有 Agent Card、Task、Message、Part、Artifact。（来源：key-concepts）
- **拆分的依据是「对方声明的技能」**：Agent Card（代理卡，一张 JSON）里列 `skills`，客户端读卡决定这个 agent 能不能干这件事、怎么发请求、怎么认证。（来源：key-concepts，Agent Cards 节）
- **任务的分层单位是 contextId 与 taskId**：`contextId` 把一串相关任务与消息归组，`taskId` 指单个任务。后续细化请求带 `referenceTaskIds` 指向原任务。（来源：life-of-a-task）
- **并行靠「同 contextId 下开多个任务」**：原文举例是先订机票，再基于机票订酒店、订雪地摩托，再基于酒店加 SPA，形成依赖树。（来源：life-of-a-task，Parallel Follow-ups）

### 6.2 怎么协调

- **没有中心调度器，只有客户端/服务端两角色**：A2A Client（客户端 agent，替用户发起）与 A2A Server（远端 agent，暴露 HTTP 端点）。客户端在这个模型里天然是编排者，原文说「The AI assistant now acts as an orchestrator」。（来源：what-is-a2a）
- **消息怎么传**：HTTP(S) 传输、JSON-RPC 2.0 作载荷格式；进度靠三种机制之一：轮询、SSE 流式、push notification（服务端回调客户端提供的 webhook）。（来源：key-concepts，Interaction Mechanisms）
- **任务状态机是协调的核心**：任务是 stateful 的，有 `input-required`、`auth-required` 这类中断态，和 `completed`、`canceled`、`rejected`、`failed` 这类终态。（来源：life-of-a-task）
- **任务不可重启**：到了终态就不能复活，后续改动必须开新任务，「Once a task reaches a terminal state... it cannot restart」。（同上）
- **协议刻意不做共享状态**：官方设计原则里的 Opaque Execution（不透明执行），原话「Agents collaborate without exposing their internal logic, memory, or proprietary tools」。对客户端来说远端 agent 是黑盒：「To the client, the remote agent is an opaque (black-box) system: its internal workings, memory, and tools stay hidden.」（来源：what-is-a2a 设计原则；key-concepts 核心角色）
- **冲突怎么裁**：协议里没有仲裁机制。歧义靠 `input-required` 状态回问客户端。（来源：life-of-a-task，Referencing Previous Artifacts 节）
- **一条可以直接引的立场**：A2A 文档专门论证「把 agent 包成 tool 是浪费」，理由是「agents are built to negotiate directly, and wrapping them as tools limits what they can do」，并给了外链《Why Agents Are Not Tools》。（来源：what-is-a2a，Problems that A2A Solves）

### 6.3 怎么跟人对接

- **人不在协议里，人被映射成两种状态**：
  - `input-required`：agent 需要更多输入才能继续，这个输入可以由客户端背后的人给。
  - `auth-required`：需要授权。
  （来源：life-of-a-task）
- 也就是说，A2A 本身**不定义审批流程**，只提供「我卡住了，等你」这个状态位。要不要弹给人、怎么弹，是客户端 agent 自己的事。这一条是**推断**，依据是协议对象里没有 approval 类对象。
- 长任务留了异步出口：客户端可以断开，服务端用 push notification 回调，适合「人不在电脑前」的场景。（来源：key-concepts）

### 6.4 承认的失败场景

明确写在文档里的：

- **不透明是有代价的**，只是官方把它当优点陈述（保护知识产权与安全），没有正面讨论可调试性下降。这一条我按**推断**处理：客户端看不到远端内部状态，出问题时只能看 Task 状态与 Artifact。（来源：what-is-a2a，Core Benefits）
- **artifacts 的版本追溯不在协议里**：原文「the serving agent shouldn't track artifact mutations, and this linkage is not part of the A2A protocol specification」，明确把「哪个版本是最新的」这件事推给客户端自己管。（来源：life-of-a-task，Tracking Artifact Mutation）
- **任务终态不可复活**，只能开新任务。（同上，Task Immutability）
- **依赖标准 Web 安全**：认证授权完全交给 OAuth2 / OIDC / API Key / mTLS 那一套，Agent Card 里声明；协议自身不解决身份问题。（来源：key-concepts，Authentication & Authorization；规范目录 §7、§4.5）

## 7. 六个项目的横向对比表

### 7.1 四问对照

| 项目 | 拆分依据 | 协调机制 | 人介入点 | 已知局限（官方承认的） |
|---|---|---|---|---|
| **MetaGPT** | **角色 + 中间产物格式**。5 个固定角色，上一环交付物（PRD、接口定义、文件清单）就是下一环的输入契约 | **共享消息池 + 订阅**，无中心调度器；不用对话用文档；代码靠「真跑单测」兜底，最多重试 3 次 | 开头提需求、结尾看产物。论文自承**中途打断与设 checkpoint 是难题** | 做不了 UI/前端；撑不住真实复杂需求；早期 review 会漏错；幻觉沿链放大 |
| **ChatDev** | **阶段 + 子任务的硬编码链**。3 阶段 5 子任务 5 角色，每子任务固定 2 个 agent（指导者 + 执行者） | 链式顺序推进；记忆分短期/长期两层；靠「让执行者先反问」去幻觉；子任务 10 轮或代码两次没变就收 | 开头一句需求，之后全自动；人只在评估环节 | 能力被高估、信息密度低；需求不清就退化；**只适合原型不适合真实系统**；通用软件无法自动评；多 agent 更贵更慢 |
| **AutoGen / AG2** | **不预设，给预设模式让你选**（轮流/模型选人/交接/编排器）。只有 Magentic-One 自带拆解 + 重规划（Task Ledger + Progress Ledger） | AG2 有 `GroupChatManager` 选人 + 广播，可选四种策略并能加「谁能接谁」的硬约束；新版 SelectorGroupChat 由 LLM 选人；终止条件收场 | `UserProxyAgent` 中途插话（会阻塞并使状态不可保存），或跑完再反馈；Magentic-One 可给代码执行加审批函数 | 团队需要更多脚手架，官方劝先用单 agent；插话会把状态搞坏；群聊会死循环；Magentic-One 有 6 条安全警告含网页提示注入 |
| **CrewAI** | **任务对象 + 显式 `context` 依赖**。顺序模式按数组，层级模式 manager 按能力派活且不预分配 | 两种 Process（顺序/层级）；同级靠两个自动工具（甩活、问同事）；Flows 提供事件驱动的确定性编排与共享 state；护栏函数拦产出 | 任务级 `human_input=True`，交最终答案前问人 | **官方不建议直接拿 Crew 上生产，让你包一层 Flow**；Crew 必须小；层级模式缺 manager 就报错 |
| **deepagents** | **上下文窗口为单位**。显式 `write_todos`（v0.7 起 opt-in）+ 隐式 `task()` 分包；官方给了「不该用 subagent」的清单 | 主 agent 调 `task()`，子 agent 独立跑完只回一份报告；isolated / fork 两种上下文模式；大块数据落虚拟文件系统；并行靠一回合多次调用或代码批量派发 | **工具级 `interrupt_on`**，改文件等危险动作前暂停，可批准/补充指示/改参数 | subagent 无状态只能回一次；fork 的子 agent 不能再派活；dynamic subagents 是 beta；官方列了三种典型失效（没被调用 / 上下文照旧爆 / 叫错人） |
| **A2A** | **协议不管内部拆解，按对方 Agent Card 里声明的 skills 派活**；任务用 contextId / taskId 组织，细化带 referenceTaskIds | 客户端/服务端两角色，客户端天然是编排者；HTTP + JSON-RPC，进度走轮询 / SSE / webhook；**刻意不共享内部状态（不透明执行）** | 协议只提供 `input-required` 与 `auth-required` 两个状态位，**不定义审批流程** | 制品版本追溯被明确排除在规范外，推给客户端；任务终态不可重启；身份问题全交给标准 Web 安全 |

### 7.2 六者拆分依据的差异（一句话版）

**同一个问题，六家给了六种答案**：MetaGPT 按「文档交接」拆，ChatDev 按「阶段对话」拆，AutoGen 按「谁下一个说」拆，CrewAI 按「任务依赖」拆，deepagents 按「上下文预算」拆，A2A 干脆不拆只负责「把活交给别人」。

### 7.3 三个可以直接拿去当论点的对照

1. **「人」的位置在往下降，也在往细里走**。MetaGPT 把人放在流程两端（提需求、看结果），并承认中途打断很难；AutoGen 把人做成一个 agent 塞进群里；CrewAI 把人挂在任务出口；deepagents 把人挂在单个工具调用前。**越往后，人的介入点越具体，但每次介入能看到的东西越少**（后者只看一个工具调用，前者能看整份 PRD）。这一条是**推断**。
2. **协调机制的两条路线**：一条是「共享消息池 + 订阅过滤」（MetaGPT、AutoGen 的广播），信息在池子里；另一条是「点对点单次交接」（deepagents 的 task 一次一份报告、A2A 的 task 对 task），信息不共享只传结果。后者更省上下文，但中途没法追问。
3. **失败大多不是模型答错，是「协调出错」**。官方示例自己就展示了两类事故：AutoGen 的 Selector 示例里 DataAnalyst 拿到错误数字算出 21.99%，以及官方为了防死循环硬加 25 条消息上限；deepagents 专门写一节 Troubleshooting 讲「没叫 subagent / 叫错 subagent」。**这两类都不是推理能力问题，是调度与实际调用问题**。

### 8.2 我不确定、需要复核的
